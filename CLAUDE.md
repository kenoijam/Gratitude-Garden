# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Gratitude Garden" is a static, dependency-free web project by Kenisha Gabriella Wijaya. Users answer reflection prompts and a flower is planted in a generative garden scene. There is no build system, no package manager, no tests, and no git repository. Every file is served as-is.

## Running it

Serve the repo root over HTTP (relative paths and `localStorage` both need an origin, and opening `index.html` via `file://` breaks the garden pages):

```bash
cd "/Users/kenisha/Uni/EXPERIMENTAL/GRATITUDE GARDEN 2" && python3 -m http.server 8000
```

Then open `http://localhost:8000/`. Entry points: `/` (landing), `/personal-garden/personal-garden-index.html`, `/shared-garden/shared-garden-index.html`, `/bouquet/bouquet-index.html`.

Note the directory name contains a space, so quote paths in shell commands.

## Architecture

Four independent pages that share a visual language but **no code**, with one exception: `garden-music.js` at the root is loaded by all four (see "Sound" below). The eight species (tulip, rose, sunflower, sakura, lily, daisy, lotus, lavender) are drawn by hand-ported copies of the same math in **seven** separate places. See "Keeping the flowers in sync" below:

| Page | Renderer | Persistence |
|---|---|---|
| `index.html` + `styles.css` | inline `<script>`, raw Canvas 2D | none |
| `personal-garden/` | p5.js global mode | `localStorage` |
| `shared-garden/` | p5.js + p5.party | realtime shared room |
| `bouquet/` | vanilla DOM + raw Canvas 2D | URL query string |

#### Keeping the flowers in sync

**A change to one flower's look must be applied in all seven sites.** They share no naming convention, so no single grep finds them all. The eight pickable species are tulip, rose, sunflower, sakura, lily, daisy, lotus and lavender; an orchid and a chrysanthemum are also drawn in all seven but are hidden from every picker, for the reason in "Two HIDDEN species" below:

| # | Site | Signature (tulip) | Role |
|---|---|---|---|
| 1 | `personal-garden-sketch.js:467+` | `drawTulipBloom(R, hue, sat, light)` | live canvas |
| 2 | `personal-garden-sketch.js:797+` | `drawTulipBloomOnGraphics(pg, R, hue, sat, light)` | preview buffer, via `drawPreviewFlower()` (`:758`) |
| 3 | `shared-garden-sketch.js:478+` | `drawTulipBloom(R, hue, sat, light)` | live canvas |
| 4 | `shared-garden-sketch.js:1230+` | `drawTulipPreview(pg, R, hue, sat, light)` | preview buffer, via `drawPreviewBloom()` (`:1477`) |
| 5 | `bouquet-sketch.js:163+` | `drawTulip(ctx, R, hue, sat, light)` | raw Canvas 2D, `ctx` first |
| 6 | `index.html:200+` | `drawTulip(R, hue, sat, light)` | hero meadow block |
| 7 | `index.html:882+` | `drawTulip(ctx, cx, cy, R, hue, sat, light)` | card-scene / catalogue block; its comment calls it "exact p5.js math" |

Both gardens carry a full 8-species preview family alongside the live one (rows 2 and 4), just named differently, so a grep for `OnGraphics` finds only the personal garden's.

**Sakura is named three different ways.** The species id is `sakura` everywhere in the *data* (mood maps, `speciesList`, saved flowers), but the drawing functions are:

- `drawSakura`: bouquet and both `index.html` blocks
- `drawCherryBloom` / `drawCherryBloomOnGraphics`: personal garden
- `drawCherryBloom` / `drawCherryBlossomPreview`: shared garden

So grepping `sakura` finds the data and never the rendering code.

**THE TULIP IS ONE CONNECTED SHAPE in all seven sites.** It was three slightly see-through pieces (a notched crown, a round bowl, a floating pale oval), which showed a darker band where they overlapped and a step where the crown's sides met the bowl. It is now a solid back silhouette rising to two outer tips, a solid front petal from the base to the centre tip, and a highlight that follows the front petal. The copies were generated from one set of shapes, so they cannot drift. `BLOOM_BOX` in both gardens and `BLOOM_METRICS` in `index.html` were re-measured for it; the ring's per species origin offset for the tulip (`cy = size*0.465`) was not, and the shift is about a pixel.

#### Two HIDDEN species: orchid and chrysanthemum

**The eight pickable species are unchanged: tulip, rose, sunflower, sakura, lily, daisy, lotus, lavender.** There are two more, `orchid` and `chrysanth`, fully drawn in all seven sites and resolvable everywhere, that appear in **no picker, no catalogue and no mood map**. Nothing can plant one. They exist so the work is not lost, and so turning them on later is a data edit rather than a drawing job.

- **Where the hiding actually happens**, and it is only these four places. Everything else already handles all ten: `SPECIES` vs `LEGACY_SPECIES` in `bouquet-sketch.js` (move the entries between the two lists); `speciesList` in `shared-garden-sketch.js`; `ratingFlowerMap`, `shaperFlowerMap` and the `votes` object in `personal-garden-sketch.js`, plus empty `keywords` arrays on the two hidden entries in `flowerMeanings`; and the catalogue tile markup in `index.html`. The drawing functions, `SPECIES_MAP`, `drawSpeciesBloom`, `bloomFns`, `flowerData`, `chipClasses`, the chip colours in `styles.css`, `defaultSat` / `defaultLight` / `speciesPetalCount` / `speciesShapeCfg` and every dispatcher already carry all ten.
- **The hidden entries keep an EMPTY `keywords` array, never a missing one.** `chooseFlowerForMood` reads `.keywords` off entries in `flowerMeanings`, so removing or renaming the field throws the moment anyone writes a journal entry. The real lists are parked beside them as `keywordsHidden`, ready to swap back. That loop also iterates `votes` rather than `flowerMeanings`, so a keyword hit on a hidden species cannot write `votes[undefined]` and poison the result.
- **Verified by exhausting the space, not by reading the maps**: all 280 combinations of rating, shaper and journal text were run through `chooseFlowerForMood`, and only the original eight ever come out.
- **Both hidden species still draw**, which is deliberate: `SPECIES_MAP` resolves them, so a share link that names one opens instead of erroring, and the sync table above stays true.
- **The orchid is a phalaenopsis face on**: three narrow sepals behind, two broad petals in front, and the lip at the bottom in a deeper tone. The lip is what makes it read as an orchid rather than a generic five petalled bloom. It is a CENTRED bloom, so unlike the lotus it needs no origin nudge, no label offset and no `bloomReach` entry.
- **The chrysanthemum is a POMPOM and that is load bearing.** A chrysanthemum is in the same family as the daisy, and drawn as a single flat bloom the two tiles are the same picture twice. Four concentric rings of short petals lightening inward reads as a ball; the daisy is one flat ring of sixteen. Checked with colour removed, which is the case that matters since a bouquet sender can set any species to any hue.
- **Both were sized by measurement.** As a multiple of R the set runs tulip 0.61, lily 0.92, rose and daisy 0.98, lavender 0.39 wide by 1.06 tall, sunflower 1.33. Orchid lands at 1.02 and the chrysanthemum at 1.17, so neither needs scaling if they are ever turned on. A spider chrysanthemum was drawn and rejected: unmistakable, but it reached 1.9R, read as tangled at garden size, and a spiky flower is the wrong shape for a meaning about quiet reflection.

#### Florist sourcing, RESEARCH ONLY, not applied to the code

This exists because the project may be made with real florists. **None of it is reflected in the eight above**, which are unchanged. The plan is for a florist orderable set to be its own separate thing for the real bouquet, not a change to the garden.

- **Six of the eight are easy**: rose, tulip, sunflower, lily and lavender are year round florist staples, and daisy is too once you say which one you mean.
- **Sakura cannot be ordered at all.** Cherry blossom sells as cut branches for a few weeks in early spring, not as bouquet stems, and drops petals within days.
- **Lotus is nearly as hard.** Fresh cut lotus is an expensive mid to late summer item moving mostly through Asian wholesale markets, and the blooms open and close on a daily cycle then collapse. Dried lotus *pods* are common year round, but that is the seed head, not the flower.
- **"Daisy" is ambiguous rather than hard.** A florist hears it and reaches for a gerbera; the drawing is a marguerite. Say which before anyone quotes.
- **Two smaller notes**: fresh lavender is summer only in most markets, dried is year round; and lily pollen stains and is toxic to cats, so florists strip the anthers for gift work.
- **The two stand ins already drawn** are the orchid, for lotus, and the chrysanthemum, for sakura. Orchid is year round from Thailand and the Netherlands with two to three weeks of vase life; its meaning is looser than lotus's, closer to grace and endurance than to rising out of hardship, and it crowds the rose's "love and depth" a little. Chrysanthemum is a top three global cut flower, cheap and year round, and carries the reflection meaning honestly through the Chinese Four Gentlemen, where it is the flower of autumn and of the scholar in contemplation. **One warning if this ever ships to Europe:** in France, Italy, Spain, Belgium and Poland the chrysanthemum is a grave flower for All Saints' Day and a bouquet of them reads as a serious misstep. No such association in Indonesia, the UK, the US or Australia, where it is a Mother's Day flower.

### Personal garden (`personal-garden/personal-garden-sketch.js`, ~2300 lines)

Single-file p5 global-mode sketch. The entire UI is built imperatively in `buildUI()` with p5.dom (`createDiv`/`createButton`/`createElement`) and inline `.style()` calls into `#ui-root`. The HTML file is nearly empty, so **UI changes go in the JS, not the HTML**.

**The shared garden's `.gg-card` is padded `34px 28px 26px`.** At 20px a 40px title sat on the card's own edge. The flower grid and the colour step set their padding inline and keep their own.

**`.gg-title` and `.gg-sub` carry their own margins.** Left to the browser's h2 and p defaults there were 33px between a title and the line under it and only 18px between that line and the field it introduced, which reads as the line belonging to nothing. They are 10px and 26px now. Screens that set margins inline, the shared garden's select card among them, are unaffected, so check for an inline value before changing these.

One exception: `personal-garden-style.css` is not the near-empty file it looks like (401 lines of `.gg-card`, focus states, ~22 classes and 11 ID rules), and it ends with a `@media (max-width: 768px)` block (`:318`) that restyles `.gg-tile`, `.gg-btn`, `.gg-title`, `#tips-card` and others, some with `!important`. `buildUI()` sets those same properties inline. Inline usually wins, but not against `!important`, so **a mobile-only layout bug can come from either file; check the 768px block before chasing it through the JS**. `shared-garden-style.css` has the same shape (`:299`).

**Both garden stylesheets now END with a phone block, and every rule in it carries `!important`.** That is not defensiveness: `buildUI()` sets the very same properties inline with p5.dom `.style()` calls, and inline beats a stylesheet on everything except `!important`. It is the only way a stylesheet can reach a p5-built interface at all. **Anything added to `buildUI()` with an inline size needs a line here too**, or it stays at its desktop size on a phone while everything around it shrinks.

- The figures, the same in both files: `.gg-card` padding `22px 18px 20px` at `width: min(94vw, 460px)`; headings 25px; `.gg-sub` and `p` 15px; `.gg-btn` and `.gg-back` 16px with a `min-height: 46px`; `.gg-grid` two columns; `.gg-tile` a 150px minimum; `.preview-holder` 120 by 86; `#tips-card h3` 17px; `#daily-note` 14px.
- **Inputs are 16px and that is a hard floor, not a preference.** iOS zooms the whole page in when a focused field is under 16px, and it does not zoom back out. Every other size on the phone can be tuned; this one cannot go down.
- **A 46px minimum on the buttons is the touch target**, not the type size. A 16px label in a box that fits it exactly is about 30px tall, which is under what a thumb reliably hits.
- **The block sits at the END of the file**, like the bouquet's. A later rule beats an earlier one at equal specificity, so a phone override written above the base declaration it is overriding does nothing at all, silently. That trap has now been hit on three separate stylesheets in this project.

- Screen flow is a `step` string (`prompt1` → `prompt2` → `prompt3` → `flowerPreview` → `garden`) that toggles `display` on the wrapper divs and gates canvas `pointer-events`. Two functions do this: `showStep(s)` (`:2162`) and `updateScreen()` (`:1611`), which duplicate the show/hide logic with different reset behaviour, so check which one your code path actually calls. `step` starts at `"prompt1"` here, but `"landing"` in the shared garden.
- `chooseFlowerForMood()` picks the species by weighted vote: mood rating +4 (`ratingFlowerMap`), "what shaped your day" +3 (`shaperFlowerMap`), +2 per keyword hit from `flowerMeanings[species].keywords` against the journal text. `flowerMeanings` is also the source of the tooltip meaning and supportive quote.
- `addFlower()` fills three depth layers (`front`, `mid`, `back`, `ROW_CAPACITY = 8` each) and picks x by sampling 80 candidates and keeping the one with the most clearance from existing blooms.
- Flowers store **normalized** coordinates (`xNorm`, `stemNorm`, `sizeNorm`, relative to `BASE_W`/`BASE_H` = 1440×900). `updateResponsiveFlowerLayout()` re-derives pixel values on every resize and scales the whole garden down if the tallest bloom would exceed `height * 0.32`.
- `draw()` paints strictly back-to-front: sky → clouds → back-layer flowers → `drawHillsBack()` → mid flowers → `drawHillsFront()` → ground → front flowers → `drawForegroundHill()`. The hills are drawn *after* their layer's flowers so they occlude the stem bases.
**Every bloom casts ONE soft drop shadow, and it is legibility rather than style.** The ground runs `#a9d9cf`, `#8fcfbe` and `#7ec4b4`, all pale teals, and the planter picks the hue freely, so a pale teal or pale blue bloom sat on that ground at almost no contrast and disappeared into the grass. `bloomShadow(f, R)` runs before the species dispatch inside `drawBloom`, in **both** gardens.

- **A shadow was chosen over an outline or a floor on lightness** because it works whatever hue is picked, and the other two fight the choice the person just made.
- **The first version let EVERY PETAL cast one and it was wrong.** It reads as petal by petal shading rather than as a flower standing on grass, because a petal's shadow falls on the petals around it. Canvas cannot shadow a group of shapes as one.
- **An exact silhouette is not available to these sketches.** It would mean rendering the bloom to an offscreen buffer, and the species functions draw through p5's globals; the only parallel families that take a buffer are the PREVIEW ones, which are separate copies, so the outline under the flower would not be the flower's own.
- **So it is ONE ellipse per bloom, drawn far off canvas and brought back purely as its own shadow.** That is what makes it a single soft shape with one alpha and no seams. `BLOOM_BOX` holds `[centre y, half width, half height]` as multiples of R, **measured** by rendering each species alone and reading back its painted bounding box, not guessed. Lotus and lavender have a negative centre y because `bloomOriginNudge` pushes their origin down and they grow upward; a shadow centred on the origin sat below the flower.
- **Canvas shadow offsets and blur are NOT touched by the transform.** p5 scales `drawingContext` by the pixel density, so both have to be multiplied by `pixelDensity()` by hand, or the shadow lands in the wrong place and comes out half as soft as asked for.
- **`SHADOW_FIT` is 0.90**, so the flower overhangs its own shadow rather than sitting inside a dark halo exactly its own size.
- **It is CENTRED on the bloom and light, not dropped below it.** A shadow cast down and to the side says the light is low and hard, which is the wrong weather for a pastel garden and read as a heavy smudge under every flower. Centred and soft it is a halo that separates the bloom from the grass and says nothing about the sun, which is what this needed to do in the first place.
- **Being centred costs contrast, and that was the trade accepted.** At `rgba(18,62,56,0.30)` offset down, the mean gain at the bloom edge was 0.21 and the average darkening 12 out of 255. At `0.18` centred it is 0.09 and 8.8. All eight species still gain: daisy 1.67 to 1.78, rose 1.65 to 1.77, tulip 1.87 to 1.98, sakura 1.35 to 1.44. **If it ever needs to be stronger, raise the alpha before putting the offset back.**

- Growth is time-based per flower (`GROWTH_STAGES.BUD/STEM/BLOOM` + `growthStartTime` from `millis()`); flowers restored from storage are forced to `BLOOM` with `isOld = true`.

**A flower GROWS, and the whole sequence is duplicated in both gardens.** `GROW_RISE` (3400ms) is the stem coming up out of nothing with a bud on its tip; `GROW_OPEN` (1700ms) is that bud opening into the bloom. `growEase` is a cubic ease-out, so it leaves the ground quickly and arrives slowly, which is the shape a plant actually grows in. `updateGrowthStages` reads the same two constants for its thresholds, so the stage a flower reports and the picture it draws can never disagree.

- **THE TIMINGS AND THE SHAPES ARE THE SAME IN BOTH GARDENS. Edit one and edit the other.** `GROW_RISE`, `GROW_OPEN`, `growEase`, `drawBudShape` and `drawFlowerWithGrowth` are character-for-character identical in `personal-garden-sketch.js` and `shared-garden-sketch.js`. A flower that took four seconds on one page and seven on the other would read as the two pages running at different speeds, which is the one thing a shared visual language cannot survive.
- **The bud is a real bud, not a small circle.** `drawBudShape` draws sepals, a teardrop body and a seam down it. A sphere on a stem reads as a pin, and the seam is what says the thing is closed and about to open rather than simply round.
- **The bloom comes OUT of the bud, it does not replace it.** Through `GROW_OPEN` the bloom scales 0.18 to 1 while the bud shrinks around it, so there is no frame where one picture swaps for another. A straight crossfade was the obvious alternative and it reads as two drawings dissolving rather than as one thing opening.
- **A BUD RIPENS THE SHORT WAY ROUND THE WHEEL, and `lerpColor` will not do it.** The skin goes from a green at hue 112 to the flower's own hue as `ripe` runs 0 to 1, and `lerpColor` moves every component in a straight line: green to a rose at 350 was therefore walked through 231, so the bud came out PURPLE on every warm flower and only looked right on the blues. `shortHue(from, to, t)` takes the shorter arc instead, sending it 112 to 51 to 350, down through yellow green and orange, which is how a bud actually colours up. Saturation and lightness stay straight lines; hue is the only one that is an angle. **Anything else in this project that interpolates a hue has the same trap waiting in it.**
- **`drawBudShape` sets `colorMode(HSL)` itself.** The gardens run in HSL, but a bud may be drawn from any call site, and a function that assumes the caller's colour mode paints grey the one time it is wrong.
- **THE LEAVES UNFOLD ON THE WAY UP, and they hold their height while the stem carries on past them.** Nothing drew them during growth at all: `drawFlowerStemAndLeaves` took over only once growth was over, so a pair of full sized leaves appeared in a single frame on a finished flower. They now come out at about one second and open over 900ms.
  - **Where they attach is a HEIGHT, not a parameter, and the two are different numbers.** `LEAF_T` is 0.60 along the stem's curve; as a fraction of the stem's height that is `bezierPoint(0, 0.4, 0.7, 1, 0.60)`, which is **0.6336**, confirmed against p5 at runtime. That figure does not depend on how long the stem is, because a rising stem is the finished one with every control point scaled by the same amount, so the 0.4 and 0.7 are constants.
  - **`stemParamAtFrac` bisects back to the parameter** that sits at a given fraction of the finished height, eighteen halvings, which is well inside a pixel. Drawn at a fixed parameter instead, the leaves slide up the stem with the tip, which no plant does; a real one puts out a leaf near the tip and then grows past it.
  - **`LEAF_AT` is the moment the tip first reaches that height**, `GROW_RISE * (1 - cbrt(1 - 0.6336))`, which is 967ms. `drawLeavesOnStem` takes an optional length multiplier and position so a finished flower calls it with neither and gets exactly what it always got.
  - **THEY FINISH WITH THE BLOOM, at 5100ms, not before it.** They first unfolded over 900ms and then sat at full size for the remaining three seconds, which made the flower the only thing still visibly growing and left the leaves reading as dropped in and stopped. `leafGrowth(elapsed)` runs from `LEAF_AT` to the end of the whole sequence, and the opening phase passes it too rather than drawing them full size.
  - **`leafEase` is a SMOOTHSTEP and it may not be `growEase`.** The stem's cubic ease-out is 0.93 done by the time the bloom starts opening, so stretching it over four seconds is the same early finish in a slower dress. A smoothstep is 0.632 there, verified at runtime, so a third of the growth is still to come while the petals open; it also leaves and arrives gently, which is what lets them start from nothing without reading as a pop.
- **NO DROP SHADOW UNTIL THE BLOOM IS NEARLY OPEN**, ramped in over the last third of `GROW_OPEN` through `drawBloom(f, shadowK)`. A bud has nothing to cast one, and switching the shadow on at the final frame would be the same pop somewhere else.
- **`bloomShadow` READS THE LIVE TRANSFORM, and that is a real bug fixed rather than a precaution.** The shape is drawn 6000 units off to the right and dragged back purely as its own shadow, and the offset and blur are DEVICE pixels the transform never touches. It used to convert them with the pixel density alone, which is right only while nothing else has scaled the canvas. The opening scales the bloom from 0.18 to 1, so an unaccounted scale of k left the shadow `6000 * (k - 1)` device pixels away: at 0.18 that is about 9800px off the left of the screen, and it slid in from there and snapped into place on the last frame. **That was the visible pop.** It takes the scale off `ctx.getTransform()` now, so a bloom drawn inside any `scale()` gets its shadow in the right place. Verified at three scales: the shadow's centre sits within half a pixel of the bloom's, and its width tracks the scale exactly.
- The old `drawBud` and `drawGrowingStem` are GONE from both files. Do not reintroduce them alongside this.

**Accounts.** `personal-garden-auth.js` owns the Supabase client, every account screen and `GardenStore`, the single place the garden is read and written. The sketch knows nothing about accounts: `loadGarden` takes `window.__gardenBoot`, and `saveGarden`, `saveName`, `hasPlantedToday` and `markPlantedToday` all go through `GardenStore`. **Keep it that way.** Anything account-shaped, including the signed-in chip, is built by the auth module against `document.body`, not by `buildUI()`.

- **Four full screen steps, and only one may be on screen.** The sign in gate, the offer to carry a browser garden into a new account, and the set-a-new-password form all carry `.gg-overlay`, and each calls `clearOverlays()` before it builds. They used to share the id `gg-auth`, and the recovery form could appear on top of a gate that the session check had already raced ahead and built.
- **Everything appends through `onReady()`.** This module runs from the head, and whether `document.body` exists when the session check resolves is a network race. On a warm cache it resolved first and the sign in screen threw on `appendChild`, which locks everyone out.
- **The gate has a way past it without an account.** "Use this browser only, no account" drops straight into the localStorage mode the project has always had. Without it, configuring Supabase would make an account compulsory to use the garden at all.
- **A browser garden is offered, never taken.** On a first sign in where the account has no row (`freshAccount`) and this browser holds flowers, `offerLocal()` asks. `GardenStore.adoptLocal()` is the only thing that copies a local garden up, and it runs once, on that answer.
- **Password recovery is an auth state event, not a URL check alone.** `onAuthStateChange` fires `PASSWORD_RECOVERY` when the emailed link is opened; the `recovering` flag stops the garden booting behind the form. The reset needs the page's address listed under Supabase's Redirect URLs, which is step 5 of `SUPABASE-SETUP.md`.
- **`signOut` had no caller for its whole life.** A device could sign in with no way out or to switch account. `#gg-account` sits **bottom right**: Home is top left, and Save PNG and the music button are both top right. Bottom right is free only because of a bug, and the two are tied together. `buildLogo` creates `#gg-logo` inside `loadImage("LOGO-01.png", ...)`'s SUCCESS callback, and that file exists only at the repo root, so from `personal-garden/` it 404s and the callback never runs. **Fix that 404 and the logo reappears exactly under the chip**, at which point one of the two has to move.

**The sketch tag is not in the HTML.** `boot()` in the auth module injects `personal-garden-sketch.js` once there is a garden to draw, because p5 starts the moment it is parsed and its `preload()` cannot wait on a promise. Put the tag back in the HTML and the garden will render before the data arrives.

**An injected sketch has to be STARTED, and `boot()` does it by hand.** p5 in global mode only auto-starts from the window `load` event, and only if `window.setup` already exists at that moment. A sketch injected after a session check has resolved misses that event entirely, so the file parses, every function is defined, and nothing ever runs: a blank garden with no error in the console. `boot()` now calls `new p5()` from the tag's `onload`, guarded on `typeof window.frameCount === "undefined"` so it cannot start a second instance if p5 did manage to start one itself. `frameCount` is the tell, since p5 only defines it once a sketch is live. This had always been broken and was hidden by an unconfigured project, where the session check resolved synchronously and the sketch was injected before `load`.

**The gate, the carry-over offer and the reset form all stand IN the garden scene.** `.gg-overlay` paints the garden's own sky, sun and three hills as a CSS background, an inline SVG for the hills over a radial sun over the sky gradient, rather than a flat wash. The sun is `circle 190px`, a fixed radius and not a percentage: a percentage grows with the window and turns the sun into a wash across the whole sky. The card on top is the project's own `.gg-card` treatment, snow at radius 16 with the garden's shadow, a Fraunces 600 heading at 26px over a 15px line, and a button identical to `.gg-btn`. The heading is 26 and not `.gg-title`'s 42 for the reason given under Type: 42 belongs to a title standing on its own above a card, and this one is inside its card.

**`personal-garden-style.css` had no `box-sizing` rule anywhere**, and text inputs default to `content-box` while buttons default to `border-box`. The sign in fields therefore hung 26px over both edges of the card while the button under them fitted. `.gg-auth-card input, .gg-auth-card button { box-sizing: border-box }` is scoped to that card on purpose; a global `*` rule would re-lay out everything `buildUI()` sizes inline.

With `config.js` left on its placeholders, nothing is gated and the garden saves to this browser exactly as it always did, so the project still runs with no setup. `SUPABASE-SETUP.md` at the repo root holds the table, the row level security and the steps. The anon key is meant to be public; the RLS policies are what actually keep gardens apart.

`last_planted` lives on the account row, not in this browser, so the once a day limit follows someone between devices rather than resetting on each one.

Local keys, used only when no project is configured: `personal_gratitude_garden` (flower array JSON), `personal_gratitude_garden_name`, `gratitude_last_planted` (MM/DD/YYYY).

### Shared garden (`shared-garden/shared-garden-sketch.js`)

Same rendering engine, different state layer. `preload()` calls `partyConnect("wss://demoserver.p5party.org", "gratitude_garden")` and `partyLoadShared("garden-" + todayStr())`. **The room key is the date, so the garden resets daily, not weekly**, and the copy on the landing page and in the garden's own tips card both say so and everyone on that date shares one room. This points at the public p5.party demo server; there is no private backend.

- `shared.flowers` is the authoritative array. `draw()` diffs `flowers.length` against `shared.flowers.length` and re-copies on change, then re-attaches local-only animation fields (`growthStage`, `growthStartTime`, `isMyFlower`) by matching on `createdIndex` + `word`.
- `partyIsHost()` guards initialization and pruning in `initDailyGarden()`.
- Flow: `landing` → `username` → `select` → `confirm` → `garden`. Here the user picks the species directly from `speciesList`; there is no mood inference. Because the choice is the user's, `speciesList` carries a `meaning` for each species and the select tiles and the confirm card both show it. ### Shared garden: likes and comments (`shared-garden-social.js`)

**The shared garden stays OPEN.** Planting is still a typed name and a sentence, with no account and no Supabase call of any kind. What needs an account is REACTING: a like has to be countable once per person, and a comment has to carry a name that belongs to somebody. A gate on the page was the other option and it was refused on purpose, since the shared garden is the one place anyone can try in ten seconds and asking for an account at the door would cost that to buy a feature most visitors never touch.

**Where a flower lives is split, and the split is the whole design:**

| | holds | resets |
|---|---|---|
| p5.party | the living garden, the authority on what is planted today | daily, with the room key |
| Supabase | one row per flower somebody has reacted to, plus its likes and comments | never |

- **The Supabase row is created LAZILY**, the first time a signed in person opens that bloom, not when it is planted. So an anonymous planter costs the database nothing, there is no anonymous insert path to abuse, and the open garden stays open. A bloom and its row are tied together by `day` plus `created_index`, which p5.party already assigns and never reuses within a day.
- **A unique index on `(day, created_index)` is load bearing.** Two people opening the same bloom in the same second would each create a row and the comments would split across the two. Losing that race is normal rather than an error: the insert fails, and the code reads back the row the other person just made.
- **`likes` carries a unique index on `(post_id, user_id)`.** One like per person is enforced in the DATABASE, not in the page, because anyone can edit the page in their own browser.
- **The sketch knows almost nothing about this.** `handleGardenPointer` calls `GardenSocial.open(f, ctx)` on a tap and `GardenSocial.close()` on a tap into empty ground. That is the entire contract.
- **`roomKey` and `speciesList` are handed over at the call site**, not read off `window`. The sketch declares them with `let` and `const`, and neither lands on `window` in a classic script. Reaching for them was the first attempt and it filed every flower under `garden-unknown`, which is one bucket for every day at once.
- **The hover tooltip is untouched.** It answers a different question: the tooltip is what the flower SAYS at a glance, the panel is what other people have said back.
- **Commenter names come from a second query, not an embedded join.** A PostgREST join would need a foreign key from `comments` straight to `profiles`, and this schema points at `auth.users`, so asking for one would be a guess about somebody else's database. The comments are fetched, then every distinct commenter in one `profiles?id=in.(...)`.
- **A profile row is created on first sign in if it is missing**, since nothing else in the project creates one and a comment with no name under it is worse than no comment. `username` must be unique, so a collision retries once with the account's own id appended, which cannot collide.
- **Supabase answers a query against a missing column with a 400 and an error OBJECT, not a thrown exception.** A plain `res.data` read therefore turns "you have not run the SQL yet" into "this flower has no comments", which is the single most likely thing to go wrong on setup. `noteError` names it once in the console and the panel says so in words, pointing at Step 6 of `SUPABASE-SETUP.md`.
- **That message once fired on a database that was PERFECTLY SET UP, and the fix is worth keeping in mind for anything that blames the user's configuration.** Three things were wrong at once. The test was `/column|schema cache|does not exist|relation/`, and "relation" and "column" appear in Postgres errors that have nothing to do with a missing table, a permission refusal among them. The flag was STICKY for the life of the page, so one bad moment at any point made every flower opened afterwards carry the same wrong explanation. And the panel never showed what Supabase had actually said, so the wrong guess was the only thing anybody could read. Now the test is only `schema cache` or `does not exist`, `clearErrors()` runs on every panel open, and the real message is kept in `lastError` and shown. **A message that tells somebody to go and run SQL has to be right, because they will go and run it.**
- **Verified against the live project with the publishable key**: `posts`, `likes` and `comments` all answer, every column Step 6 creates is present, and the exact query the panel runs returns cleanly. An RLS refusal comes back as `new row violates row-level security policy for table "posts"`, which is correctly NOT a schema problem.
- **Signing up with confirmation emails left on returns a user and NO session.** The panel says to check the email rather than looking signed in while every write is refused.
- **The whole feature is optional.** With no project configured, or with the Supabase library missing, `GardenSocial.open` does nothing and the garden behaves exactly as it did before any of this existed.
- **(Resolved) The panel's phone layout could not fire for its whole life.** It becomes a bottom sheet under 560px, and `shared-garden-index.html` had no viewport `<meta>`, so a phone reported a 980px layout viewport and took the desktop side panel. The meta is in now and the sheet works: 375 wide, anchored to the bottom, 74vh.

**The key check moved to `config.js` as `window.readSupabaseConfig()`.** Both the personal garden's gate and this module need exactly the same one, and two copies of the rule that keeps a SECRET key out of a web page is one copy too many. It is the same function, moved: re-tested after the move on all eleven cases, 8 refused with their own reason and 3 accepted, the `service_role` JWT payload decode included.

### Bouquet (`bouquet/`)

The only page with real HTML markup and a real stylesheet. A seven-step wizard (`STEPS = ["flowers","foliage","wrap","card","letter","bg","reveal"]`) writes into one module-level `state` object; `goToStep()` toggles `.bq-step` visibility. Adding a step means touching four things: `STEPS`, the progress dots in the HTML (`data-idx` must stay in step order), the back and continue buttons in `initNav`, and `encodeState`.

The share link is the storage: `encodeState()` compacts `state` into short keys and base64url-encodes it into `?b=`. `boot()` checks for `?b=` first, and if present it hides the builder entirely and renders recipient view via `renderFinal(true)`, falling back to `#bqLinkError` if decoding fails. Anything added to `state` must be threaded through `encodeState`/`decodeState` or it silently will not survive sharing.

**Old share links must keep opening.** `decodeState` spreads a pre-per-species `h` across every species, defaults a missing `g` to `leaves`, and `WRAP_ALIASES` maps the three wrap ids the patterned set replaced (`marigold`, `ivory`, `plum`) onto papers that still exist. It also fans `f` when the link carries no `a` key: see "The stored order IS the arrangement" below. Wrap **ids never change**, only their names and colours, so a link naming `blush` still opens even though that paper is now called Peach and is no longer pink.

Conventions here that differ from the rest of the project:

- **Paper is a COLOUR and a PATTERN, chosen separately.** There were nine fixed colour-plus-pattern papers and every one collided with several flowers: against the eight default hues the worst case ran 1.02:1 to 1.27:1, and `dots` at hue 344 is the rose's hue exactly. No fixed set can fix that, because the sender also moves each species' hue. So `PATTERNS` holds six patterns, each carrying its own **saturation**, which is what keeps newsprint grey and kraft muted at any hue, and the sender sets hue and lightness with two sliders. `ink` is derived as 35 lightness steps below the paper at slightly more saturation; `ribbon` sits 165 degrees round, so it always separates from the paper.
  - **`currentWrap()` is the only thing that decides what gets drawn**, and `renderBouquetCanvas` now takes either an id or a built object. The landing page still passes the id string `butter`.
  - **The nine `WRAPS` are not gone and must not be deleted.** Every link made before this names one, and `state.legacyWrap` keeps it a preset so it renders with its hand-picked ribbon and ink rather than derived ones. Touching any control clears `legacyWrap`, since the sender has taken the paper over. All twelve old ids, the nine papers plus the three aliases, were checked to open with their exact original values.
  - **The link carries `wh`, `wl`, `wp`** for a built paper, or `w` for an untouched legacy one. `decodeState` accepts both.
  - **The default paper is `h225 l45`, and it was chosen by sweeping, not by taste.** Butter at lightness 76 warned on sight for most bouquets: hue 47 against a daisy at hue 52 is 5 degrees apart at 1.15:1. Sweeping every hue against all eight species, **nothing between lightness 46 and 93 carries the whole set**, and the only pale one that does is a near white mint at 94, which is the flat sheet failure the papers were darkened to avoid. This is the lightest paper that carries every species with margin, 4.03:1. Mid tones are the problem, not darkness.
  - **The check weighs HUE as well as luminance.** A bloom passes on a 2.0 luminance ratio, or on 1.5 once it is more than 60 degrees of hue away. Luminance alone is both too strict and too lax: a red rose on a navy stripe measures 1.62 and reads perfectly, while the same 1.62 between two pinks is mud. Same pairing the landing page's card colours were settled on. A pattern's saturation changes the paper's luminance, so switching pattern can flip the verdict; that is correct, not a bug.
  - **`PAPERS` is the twelve a florist actually wraps in**, four columns by three: Kraft, Newsprint, White, Butter, Blush, Sage, Lavender, Cellophane, Burgundy, Forest, Navy, Black. **Half of them fail the check and that is the point.** Newsprint, white, blush, sage, lavender and cellophane are pale by definition, and these flowers live at lightness 52 to 72, so no tuning makes them pass against a daisy; darkening a blush until it clears turns it into a dusty rose and the name stops matching the swatch. The four that always work are Burgundy, Forest, Navy and Black. A dark bouquet on a pale paper is lovely, and the check line is what says so per bouquet.
  - **Three of the twelve were retuned, and the ids did not move.** A `PAPERS` entry only sets the sliders, so unlike `WRAPS` nothing in a link names one and their colours can change freely; `id` is kept only so the grid can mark which swatch is current.
    - `cream` is **Newsprint**, `h210 s4 l88`, the grey the newspaper pattern already prints in rather than the old warm ivory. It clears 6 of 8; going darker makes it worse, not better, which is the mid tone rule again.
    - `charcoal` is **Black**, and it went `h210 s10 l24` to `h215 s6 l16` so the name is true.
    - `black` became **Butter**, `h47 s92 l76`, and it is **`butter` in `WRAPS` exactly**, ribbon hue 12 and all, so the landing page bouquet and the builder show one yellow rather than two. It clears 5 of 8, failing the sunflower, the daisy and the lily, which hue 47 always will. It briefly held a Terracotta, `h16 s55 l40`; that was the only paper ever kept at a deliberately worse ratio than it could have, on the argument that a darker one renders as chocolate and Kraft is already the brown.
    - **This is also the only `PAPERS` id that has ever changed**, `black` to `butter`, and it is safe for a reason worth knowing: a `PAPERS` id never reaches a link (`encodeState` writes `wh`/`ws`/`wl`/`wp`/`wr`, never a paper id) and `refreshWrapStep` marks the current swatch by comparing `h`/`s`/`l`/`p`, not by id. Only `WRAPS` ids are load bearing.
  - **`kraft` went LIGHTER, from `l66` to `l76`, and it improved the contrast.** That is the mid tone rule cutting the other way: at 66 kraft was sitting in the trap and cleared 1 of 8, at 76 it clears 3, because the dark blooms separate from it once it moves toward the pale end. It still warns on a pale bouquet, which is honest for a real kraft wrap. **`WRAP_DEFAULT` holds the same numbers and must be changed with it.** No real link depends on that default, since `encodeState` always writes `wh`, `wl` and `wp` together; it only fires on a malformed link.
  - **Saturation belongs to the PAPER, not to the material.** It used to come from the pattern, which drove Sage to a vivid green and Cream to a beige, because linen and korean carry a saturation suited to a coloured sheet while a neutral has to stay neutral whatever it is woven from. `state.wrapS` holds it, the material's own figure is only a fallback for a link that names none, and the link carries it as `ws`.
  - **Kraft is the default**, `h28 s38 l66`, and it is what the flowers step previews while you pick. It measures 1.04 against a lily, so on a pale bouquet the check warns from the first screen. That is the honest state of a real kraft wrap, and the sliders are one drag from changing it. Free sliders lost the curated starting points the old nine gave, which is a real cost: a sender should not have to build a colour from nothing. These were checked against all eight species instead of picked by eye, and each carries its worst ratio in a comment. **Picking one only SETS THE SLIDERS**, so a swatch is a starting point rather than a mode and there is still one system underneath.
  - **`kraft` is in that list knowing it fails, and that is deliberate.** A classic brown paper tan measures 1.04:1 against a lily and **no tan clears the set**: brown's hue sits near the sunflower, lily and daisy, so hue distance cannot rescue it the way it rescues forest green and teal, which both work at lightness 95. Brown only clears at lightness 24 to 25, a dark chocolate, which is `cocoa`. Kraft is offered anyway because brown paper is what a bouquet actually comes in, and the check line tells the truth per bouquet: fine behind roses and lotus, poor behind daisies and sunflowers.
  - **The ribbon is muted, `s: 46, l: 72`.** At 72 saturation it came out a hot coral or a hot green beside pastel blooms and pulled the eye off the flowers. The hue still comes from the paper, which is what keeps it separate; only the shout is gone.
  - **The ribbon does NOT follow the paper.** Each of the twelve papers carries its own hand-picked `r`, so choosing one sets the ribbon once; dragging the paper hue or lightness afterwards leaves it exactly where it is, and the ribbon slider overrides it for good. It used to be derived 165 degrees off the paper hue and recomputed on every slider move, which made it slide around under the sender while they were still choosing a colour. It is written to the link as `wr`.
  - **A pattern's ink goes the way there is ROOM, via `inkFor()`.** Fixed at 35 steps darker it vanished on a dark paper, and most papers are dark now that mid tones are out. Above lightness 55 it goes down, below it goes up. Newspaper, Polka dot, Gingham and Stripes all take it.
  - **Newspaper, Polka dot and Crinkle were painting in hard-coded colours** left from when each paper was one fixed colour: newsprint at hue 210, dots at a near white 350, fibres at browns 26 and 34. On a blue sheet they were brown specks and invisible dots. They derive from the paper now. If a new pattern is added, give it `wrap` and derive.
  - **Six materials, and between them they cover the whole range**: nothing, print, crease, weave, grid, film. Solid, Newspaper, Kraft, Linen, Grid, Cellophane. Korean wrap, tissue and deckle edge went because each was a subtler version of one of these and the row stopped being a choice.
  - **Grid is a PRINT and Linen is a WEAVE, and the numbers keep them apart.** Grid is a single thin rule every 26px; linen is threads every 5px at a low alpha with the odd slub. Drawn at similar densities the two are indistinguishable, which is why the gap is deliberate.
  - **`paintPattern` still handles six retired ids**: `korean`, `tissue`, `deckle`, `dots`, `gingham` and `stripe`. The first three came and went this session; the last three are named by `WRAPS`. **Delete any of those cases and old links break.**
  - **Kraft is deliberately soft.** At 34 creases with a 20 step tonal swing it read as crumpled foil; kraft is matte and its folds are gentle. It is 20 creases at half the swing and thinner lines.
  - **Cellophane is the one wrap you see through, and it needed no reordering.** Everything green and every bloom is already painted before the paper goes on, which is the rule the whole composition rests on, so `paintPanel` just drops the panel's alpha when the material carries a `sheer` figure. `patternCello` then paints its gloss at full strength on top. Reset `globalAlpha` at the end of `paintPanel` or every later panel inherits the sheerness.
  - **Crinkle was Brown paper, and it is creases now, not fibre.** The old texture was a speckle at 0.10 alpha and the honest answer to "what is the difference between Plain and this" was almost nothing. It draws 34 creases, each a shallow three point curve with a lit side and a shadowed side, both toned from the paper. **The id is still `kraft`**, because links name it; only the label changed, since the paper is whatever colour the sender picked and calling it brown described something it no longer is.
  - **The check line is the point of the rebuild.** `wrapContrast()` measures the paper against every bloom actually in the bouquet and warns below 2.0, with an "Adjust it for me" that calls `fixWrapLightness()`. That moves lightness the LEAST distance that clears, in whichever direction is nearer, which is often **darker**: with blooms spread over lightness 52 to 72, going up runs into the pale ones first. `goToStep` re-runs it on arrival, because the bouquet it measures against was still being picked when the step was built.
- **Every preview column carries the picker's own label, and that is load bearing, not decoration.** `.bq-pick-layout` is `align-items: start`, and the preview was the one thing on the step with no label above it, so its frame began level with the picker's LABEL rather than with the picker's first tile and rode about 22px high. Both boxes now start at 323px on the foliage step. `.bq-preview-col` had to become a flex column for it.
- **The last three steps preview the REVEAL, not just the note.** The card colour, the words and the backdrop were each chosen blind and only met at the reveal. The first version showed the note alone, which dropped the bouquet halfway through the wizard and stopped the preview being a preview of the same object; it is the bouquet, the card tucked into it, on the backdrop, and **only what the step is choosing changes**. Every holder paints the backdrop, so the ground does not change under the sender between step 4 and step 6.
  - `refreshNotePreviews(repaintBouquet)` walks every `[data-note-preview]` on the page, since the three steps are three separate sections and a single node cannot sit in all of them. Driven from the letter inputs, from picking a card colour or a backdrop, from `goToStep` and from `initResize`.
  - **The bouquet is repainted only when asked.** Typing fires this on every keystroke, and rebuilding an arrangement per character is real work for a picture that has not changed, so the letter step passes `false`. The `clientWidth > 0` test is the other half: a canvas on a `display: none` step measures 0 and `renderBouquetCanvas` falls back to a 320 wide bouquet, which then has the wrong height set on it when the step is finally shown.
  - **`data-note-mode` says whether the card is shut or open.** Shut on the card colour and backdrop steps, open on the letter step, which is the one where the words have to be readable while they are typed.
  - **The open note is anchored to the BOTTOM of the stage, not centred on it**, at 86 percent width. Centred and full width the bouquet came out as two slivers above and below, which reads as a note with an accident behind it. Anchored low it grows upward like a card lifted out of the wrap and the blooms stay visible above it: 94px of bouquet with a normal message, still 36px with the full 600 characters, where a centred note would have run off the top.
  - **The message scrolls inside the note rather than growing it**: a 600 character letter would otherwise push the preview past the picker beside it and the step would resize as it was typed, which is the exact thing the 980px card was unified to stop. It is left genuinely empty rather than filled with a placeholder string, so the stylesheet's `:empty` rule can show the grey hint.
  - **The preview column stays 280px on all six steps.** The card tag overlaps the wrap rather than sitting beside it, which is how the reveal composes them anyway, so a bouquet and a card fit. Widening only the last three would make the frame jump between steps 3 and 4, which is the resizing the card was unified to stop.
  - `.bq-note-bouquet` carries `data-no-tooltip`: these are illustrations of a choice being made, not a bouquet anyone is exploring, the same reason the landing page's examples opt out.
- **The drag hint is INSIDE the preview frame now**, pinned across its top at `z-index` 2 with `pointer-events: none`. The bouquet paints from about a fifth of the way down its 400 by 500 box, so the hint sits on canvas the bouquet never reaches.
- **The wrapping paper is painted on the canvas, not layered over it,** and it is ONE sheet. `CONE_TOP_HALF` / `SHOULDER_Y` / `SIDE_CURVE` define a single silhouette; `paperBack` and `coneFrontPath` both use it, and `coneRightSide` / `coneBottomAndLeftSide` are literally shared, so the sides of the front meet the back exactly. The sheet behind rises to ONE point at the centre (`BACK_TIP_Y`), each side sweeping up to it in a single curve: a row of separate corners reads as several bits of paper rather than one folded sheet. `SIDE_CURVE` holds the sides wide well down the sleeve before they draw in, which keeps the opening broad; a straight taper narrows it far too fast.
- **A bouquet is 5 to 12 stems** (`MIN_FLOWERS` / `MAX_FLOWERS`). Five is the floor because three left the wrap looking empty however the foliage was tuned. Bouquets shared before that floor existed can hold fewer and still render correctly: `decodeState` only requires at least one, the renderer takes any count, and the minimum applies solely to bouquets being built now. Every count-based tier below therefore keeps its branches for 3 and 4, which now serve only those older links.
- **Three things are sized from the stem count,** all by `setNotchForCount`, which `buildArrangement` calls itself rather than trusting the caller so the paper and the bloom placement can never work from different values: `NOTCH_Y` (a deep opening under few flowers is mostly bare paper), `BACK_TIP_Y` (a tall point over a small bunch is a paper cone with a few flowers in it), and `STEM_COUNT`, which the greenery reads for density and length. Spread the tiers over the range that can actually occur: when the minimum moved to five, tiers that stepped at four and six put nearly every bouquet in the top tier and the variation collapsed. The front sweep's control point is tied to `NOTCH_Y`, not a fixed height, or a shallow opening ends up with its control above its own end point and the curve inverts.
- **The bunch may be wider than the paper, but only above it.** `BOUQUET_HALF` exceeds `CONE_TOP_HALF`, so flowers spread past the wrap once they clear the shoulder, which is how a real bouquet sits and what stops a small sleeve looking empty. Below the shoulder the sleeve is the limit, so nothing ever pokes out of the side of the paper itself. `ENVELOPE_BLEND` eases between the two, or blooms just above the paper snap outward.
- **Everything green and every bloom is painted BEFORE `paperFront`.** The paper then cuts across whatever sits low in the opening, which is how a real bouquet looks, and it is also why nothing can end up perched on top of the sleeve. Combined with `clipToEnvelope` it is what keeps leaves from straying outside the wrapper: below the paper edge they are hidden, wider than the sleeve they are clipped.
- **Three geometry helpers, and they must agree.** `coneHalfWidth(y)` is how wide the paper is; `frontTopAt(x)` is where the front edge sits, and is kept in step with the drawn path by hand, so change both together; `envelopeHalf(y)` is how wide the bouquet may be at a given height.
- **Patterns are painted through a clip.** Each panel builds its path then calls `paintPanel(ctx, wrap, dl)`, which clips, fills the base tone, runs `paintPattern`, then lays a translucent shade for folds. Every pattern is drawn across the whole 400x500 space rather than per panel, so one continuous sheet runs across the creases, and all of them are seeded so a link rebuilds identical paper.
- **Palette colours live in the JS, not the CSS.** `WRAPS`, `CARDS` and `BACKDROPS` are HSL values applied to swatches inline, because the canvas derives fold and shadow tones arithmetically via `tone()`. There are deliberately no `.wrap-*` / `.card-*` / `.bg-*` classes. Each `WRAPS` entry carries its own hand-picked `ribbon` colour, since a tone derived from a patterned sheet has nothing consistent to sit against.
- **Paper is a background, so it has to be darker than the flowers.** Sage, blush, polka dot, gingham and stripes all sat between lightness 70 and 94, at or above the pale blooms, and the bouquet came out as a flat sheet with slightly different pale shapes on it. They were brought down until there is something behind the flowers; measuring the median luminance change where blooms are painted over paper, sage went 91 to 133 and stripes 69 to 104. Only two pale papers remain, newspaper and brown paper, and both carry a dense printed pattern that holds the bunch on its own. Blush and polka dot were also the same pink to within four degrees of hue, one plain and one dotted, which is not two choices: `blush` is now a warm peach, and `picnic` is named Gingham after the pattern it actually draws. **The ids did not change**, only names, colours and ink.
- **Colour is per species, not per bouquet.** `state.hues` maps species id to hue, `hueFor()` falls back to that species' default in `SPECIES`, and `stemHue()` nudges individual stems of the same species a few degrees apart by seed. Each flower tile carries its own slider. Only hues that differ from the default are written to the link, under `hs`.
- **Every swatch carries a measured hairline, and it has to be a pseudo element.** The pale swatches had no edge at all: White is `#f8f8f7` on the paper box's cream `#fff9e3`, which is **1.01:1**, and the ring it replaced was 0.08 alpha, so at 1.06:1 it did not outline the tile it was drawn for. Newsprint was 1.25 and Cellophane 1.17, and Snow on the card grid and Cream on the backdrop grid are the same colour as the page behind them. `.bq-swatch::after` at `rgba(29,100,102,0.28)` measures 1.53:1 against a White tile and 1.55:1 against the cream box, while staying at 1.21:1 on the Black tile so it does not shout on the dark papers. **It cannot go back to being an inset `box-shadow` on `.bq-swatch` itself**: the paper and material swatches carry a `.bq-swatch-canvas` at `inset: 0`, and a positioned child paints over an inset shadow. The check badge is z-index 2 and stays above the ring's 1.
- **Twelve papers at four columns, six materials at three by two at every width.** Left on `auto-fit` these reflowed into uneven rows as the column narrowed and at the narrowest collapsed to one, so every one of these grids is a fixed count with a media query rather than `auto-fit`.
- **The wrap step's two columns must come out level, and the ratio is what does it.** The three sliders sat under the paper swatches, which made the left column a label, three rows of swatches, three sliders and the check line against a right column holding a label and three rows of tiles: 391px against 336, and the left box came to rest directly on the nav buttons. The sliders moved right, which flipped it to 391 against 558 and pushed the card past its 700 `min-height`. Both fixes are needed together: the material grid went to three by two so the right column loses a row, and `.bq-wrap-controls` went from `1.6fr 1fr` to **`1.25fr 1fr`**. Measured after: 383 and 385, card back to 700, material tiles 81px rather than 69, and 132px of clearance above the buttons. **Check both columns and the card height after touching either one**, since the two move against each other.
- **`.bq-wrap-controls` is `align-items: stretch`, and it has to be.** The left box's height follows how many lines the check message wraps to, so at `start` the two columns lined up only by coincidence: on a paper that passes the message is one line, the box ended at 660 and the ribbon slider hung 21px below it, while a warning wrapped to two lines and they matched. `.bq-wrap-check` also reserves **two lines** (`min-height: 2.9em`), or the whole block grows and shrinks by 21px every time a swatch is clicked, which is visible movement directly under the cursor doing the clicking. Both are needed: stretch levels the columns, the reserve stops the step breathing.
- **The three sliders are one group under one heading.** As three peers of the Material label above them, "Or mix your own" sat directly under the material tiles and read as being about the material. `.bq-slider-group` carries the picker label and the three inside it take `.bq-control-sub`, which is lighter, so the column has one level of hierarchy rather than four labels of equal weight.
- **`.bq-nav` carries `padding-top: 30px` as well as `margin-top: auto`.** The auto margin is what keeps Continue in the same place on every step, but it gives NO gap at all on a step whose content already fills the card: on the catalogue and the template gallery the last row of pictures ran straight into the Back button and the two read as one block. The padding is a minimum the auto margin cannot provide. Measured after: every step has at least 30px from its last content to the buttons.
- **One card, every step: 980px, and the number is not arbitrary.** It is the widest the card can be while the flower grid still holds four columns, since five need 646px of content and 980 leaves 620 after the padding, the 280px preview and the gap. Wider and the eight species fall 5 and 3. Before this the card was 640 on four steps, 900 on flowers and 1040 on wrap, and the preview shrank from 280 to 260 on the wrap step, so the page resized as you moved through the wizard: measured heights ran 722, 800, 843, 532, 539, 532. **`.bq-card` carries `min-height: 700px` and `margin-top: auto` on its nav**, which puts every step within 5px of the same height and the Continue button within 5px of the same place; it had been jumping 145px. The three text-only steps cap their own content at 620px and centre it, so a wider card does not stretch a letter into a banner. Mobile clears the min-height, since there you scroll.
- **Blooms can be pointed at.** `renderBouquetCanvas` records every bloom's centre and radius on the canvas as `_blooms`, converted to CSS pixels so a pointer position needs no rescaling, and `attachBloomTooltip` hit tests it back to front. One `pointer` handler serves both hover and tap: it branches on `pointerType`, so a mouse gets hover and a finger gets tap, with a second tap dismissing. It applies to the live preview and the received bouquet, but a canvas can opt out with `data-no-tooltip`, which the landing page's examples do: those are illustrations, not a bouquet anyone is exploring.
- **A tier holding one stem puts that stem at its own midpoint.** With four stems or fewer every tier holds exactly one, so the whole bunch used to collapse onto the centre line as a vertical stack of overlapping blooms. `wholeBunchFan` measures the fan across the bunch as a whole below that count, and widens `spreadX` while it does, since the count based width is at its narrowest exactly when the stems most need telling apart. A finished bouquet is at least `MIN_FLOWERS`, so this shows in the live preview while picking and in share links made before that minimum existed.
- **The drag hint sits ABOVE the preview,** not under it, so it is read before the bouquet rather than found after it, and it only appears once there is a bouquet to rearrange.
- **The word in the interface is "foliage", never "greenery".** The step was called both, one in the progress dots and the other in its own heading. The code names follow it (`state.foliages`, `FOLIAGE`, `foliageSprig`, `#foliageGrid`), with the single exception of `greenery(ctx)`, the drawing pass. Landing page copy uses the same word.
- **Foliage is a sender choice, and it is drawn in three passes.** A scattered backdrop across the whole bunch first, then a fan rising from under the opening, then a weave low among the fill blooms. The backdrop is the one that stops the bouquet reading as empty: the fan radiates from a single point, so by the time it reaches the flowers it has spread far too thin to fill the gaps between them. Eight kinds including "None", which is the flower grid's count exactly, so the picker fills four columns by two on a wide screen and two by four on a phone with no orphan tile either way, and **up to two can be chosen and mixed** (`state.foliages`, capped by `MAX_FOLIAGE`). With two, each draws about 0.62 of its usual density and is nudged round by a different angle, so a pair reads as a fuller mix rather than simply twice the foliage. "None" is exclusive: picking it clears the rest, and picking a real kind drops it. A third pick pushes the oldest out rather than being refused, so the tiles never dead end. `decodeState` accepts all three shapes the `g` key has had: absent, a single id, and an array. `FOLIAGE` entries carry their own `sprigs` and `collar` counts and colour; all three passes then scale their count and length by `STEM_COUNT`, since foliage tuned for nine stems buries three. Per kind counts are not interchangeable: eucalyptus has much the largest leaves, so the count that suits fern or baby's breath turns the middle of the bouquet solid green, and it runs deliberately lower than the rest. `collar` is the low central pass, so cutting it is what thins the centre specifically. `foliageSprig()` draws one sprig along a shared quadratic, and how much it carries follows its own length: with a fixed count the long sprigs came out as bare wire with a couple of leaves stranded at the end. `renderFoliageTile` calls the same routine, so a tile cannot drift from what the bouquet draws.

  - **Berries and Bear grass are the two that took the set to eight**, and both were picked to be unlike the five already there rather than to be classic: olive and ruscus are the obvious florist greens and both draw pointed leaves up a stem, which is what Leaves already is, so a grid holding all three would read as one choice printed three times.
  - **Berries is the only kind carrying two colours.** Its `hue`/`sat`/`light` is still the GREEN, because the shared stem stroke at the top of `foliageSprig` reads those three and a red stem is nonsense; the fruit rides along as `accent`. Three fruits to a cluster, not one, since a single circle on a spur reads as a bead on a wire, with the back two darker and one highlight on the whole cluster rather than on each fruit. Its counts were first set low on the reasoning that a cluster weighs more than a leaf; rendered, the bouquet came out visibly emptier than the same one under eucalyptus, so they run with the rest of the set.
  - **Bear grass skips the shared stem**, the only kind that does apart from `gyp`, because the stem IS the blade and there is nothing to hang on it. Each blade is a filled taper rather than a stroked line, or it reads as wire, and the per blade bow is what stops three blades from one origin looking like a drawn asterisk. Its blades were thinned from 2.2 to 1.7 at the base: at the original width three sprigs read as an agave rather than as grass.
- **The band spans the paper, measured not assumed.** It reads its width from `coneHalfWidth` above and `tailHalfWidth` below, at its own height, plus a hair of overhang. Fixed at 30 either side it was narrower than the roughly 39 the sleeve is there, so the ribbon looked like it was sitting on the wrap rather than passing around it.
- **The ribbon is a flat bow with no band behind it.** A band across the paper kept reading as a printed stripe. It is fill only, no outline, the fold inside each loop drawn as a darker shape rather than a line, and nothing symmetrical. Two scales apply: the whole bow is scaled as a unit so its proportions stay put while it is sized against the sleeve, and the loops carry a second, smaller scale of their own, since at the same size as the rest they ran about two and a half times the width of the gathered paper and made the bow read oversized. The two tails part at the knot and sweep away in opposite directions: crossed tails read as a drawn symbol of a bow, parted ones read as ribbon.

**The stored order IS the arrangement.** `buildArrangement` used to call `fanOrder` on its input every render, which meant a stem's place was derived and could not be edited. `fanOrder` now runs in exactly two places: `changeFlower`, so repeats of one species still spread through the bunch rather than being dealt in a row, and `decodeState` for links made before this. Everywhere else `state.flowers` is taken as the order it is dealt in, each stem carries `st.idx` back out through `canvas._blooms`, and dragging one bloom onto another is a swap of two array entries. `encodeState` writes `a: 1` to say the list is already in arrangement order; a link without `a` is older and gets fanned on the way in, so it renders exactly as its sender saw it.

**Dragging swaps, it does not reposition.** `attachBloomDrag` is attached only to a canvas carrying `data-drag-swap`, which is the flowers step's live preview and nothing else, and it sets `touch-action: none` on that canvas so a finger drag is not read as a page scroll. A free drop was the alternative and it fights the sender: `settleTip` pulls every bloom back inside the envelope and above the front paper edge, so a flower dropped low or wide visibly springs somewhere else. Swapping keeps the shape the arrangement gave the bunch and moves only which flower stands where. The rings drawn during a drag go straight onto the canvas under a reset transform, since `_blooms` is recorded in CSS pixels already.

**Composition.** Blooms are placed first and stems drawn to reach them, the reverse of how it once worked. `buildArrangement` deals the sender's stems round robin into the three `TIERS`, back, middle and front. Each tier sits lower, narrower and slightly larger than the one behind, and alternate tiers carry a half step `stagger` so blooms fall into the gaps of the tier behind rather than lining up in columns. Two tiers is not enough: a dome plus a low fill leaves a visible gap across the middle and reads as two rows. Height within a tier comes from each flower's own seed, since a repeating pattern of fixed offsets reads as rows. `relaxTips` packs blooms at 0.62 of their combined radius rather than holding them a full radius apart, because real bunches overlap and polite spacing leaves paper showing between every flower. `settleTip` enforces the only two rules: a bloom must sit inside the envelope, and its centre must stay above the front paper's edge so it is never mostly hidden. The paper may still cut across its lower petals, which is exactly how a flower down in the wrap should look.

Things learned the hard way here, all of them only visible by rendering and looking:

- The fill blooms must follow the V down, lowest in the middle. Sat level across, they leave a wedge of bare paper below them, and seeing flowers there is the entire point of dropping the front.
- The greenery fan starts just under the opening, not at the tie. Started at the tie, almost every sprig falls behind the front of the wrap and the foliage choice does nothing. It is also kept fairly upright, since sprigs thrown wide land under the sweeping edge and are swallowed, and long enough to reach up between the blooms or a full bouquet simply covers the lot. Roughly every third sprig is a long one that breaks the top line, since cut foliage never comes trimmed to a single height.
- Foliage colours need real saturation. At sat 16 the eucalyptus was drawing perfectly well and was still invisible against kraft.
- Bloom size is a composition control. Large heads sit three across the mouth of the wrap and swallow everything behind them.

`bloomReach()` is how far a species paints below its origin. Lotus and lavender grow upward from an origin that `bloomOriginNudge` pushes down, so their reach is a small constant rather than the radius, and it already accounts for the nudge: do not add the nudge on top of it when reasoning about clearance.

**The reveal must not depend on `requestAnimationFrame`.** It does not fire while the document is hidden, and a link opened in a background tab, the normal case when tapping a link in a chat app, left the recipient with a blank stage: nothing painted, and the `revealed` class that fades in the canvas and the card never added. `renderFinal` paints synchronously, again on a timeout, and `initResize` redraws on `visibilitychange` and `pageshow`.

**Tile grids use `auto-fit`, not a fixed column count.** A tile's min content width is its 100px canvas plus padding, so a fixed `repeat(3, 1fr)` could not shrink below about 126px per column and the last column overflowed the grid and slid under the sticky preview panel.

**The flower tiles carry the name and the meaning only.** They used to carry a three line blurb under the meaning as well, which made the picking screen far taller than it needed to be; the shared garden's tiles show a name and a meaning, and these now match. `.fblurb` stays in the stylesheet because the foliage tiles still use it for their note.

**The flower tiles are centred.** They were left aligned for a while, on the argument that centred text starts at a different x on every line and a grid of tiles then has no common edge to read down. That was overruled: the picture and the stepper were centred anyway, so the words hanging left read as misaligned with the flower above them rather than as a column. `.bq-tile-hue` needs `align-self: stretch` under `align-items: center`, or the slider shrinks to its content. The blurb reserves a fixed three lines rather than relying on its character count: the eight blurbs are all 34 to 36 characters, but lavender's shorter words pack into fewer lines and left its tile shorter than the rest. Equal characters does not mean equal lines.

**The letter tag sits BEHIND the canvas** (`z-index` 1 against the canvas's 2), overlapping the sleeve. The canvas is transparent everywhere the bouquet is not painted, so the paper hides the card's inner edge and it reads as genuinely tucked into the wrap rather than propped beside it. Its position is a balance: pushed further in, the sleeve covers "Tap to open" and it stops reading as tappable.

**Every dimension in `drawLavender` scales with the height it is given.** The petal width was once a fixed 14 regardless, so when bloom sizes came down the spike kept its old width and read as short and fat. The ratios in there are the original numbers divided by the height they were drawn at; if you change one, change them as a set.

**A canvas is a bad flex item.** It carries an intrinsic size, and flex items may shrink below their stated width, so a canvas set to `width: 100%` inside a flex container collapses to its own intrinsic width instead of filling the box. Both the landing page card and one of the throwaway test harnesses hit this. Use `display: block` with `margin: 0 auto` to centre a canvas, not flex.

The previous version of all three files is kept in `bouquet/_previous/` since the project has no version control.

#### Physical: a mock Indonesian checkout

- **`CITIES`, `FLORISTS` and `CATALOGUE` are placeholder data**: **two** cities with their own ongkir, three florists each, and **six** bouquets attributed round robin so the catalogue always reads as local without needing six entries per city. #### Digital: nine templates

- **A template holds FIVE species, and where the repeats fall is a rule rather than a preference.** Ten stems drawn from two or three species read as a bunch of one flower with a garnish, which is not what a template is for. Two rules hold, and both were checked programmatically over all the templates rather than by eye:
  1. **No two NEIGHBOURING entries in `state.flowers` may be the same species.** The list is dealt round robin into the three tiers, so neighbours land side by side in the same region of the bunch.
  2. **A species' copies must sit at indices whose remainder on THREE differs.** There are three tiers and `buildArrangement` deals `index % 3`, so two copies at 2 and 5 both land in the front tier however far apart they look in the array. Rule 1 alone passes that pair and the bouquet still comes out with the repeats stacked.
- **Checking the array is not checking the bouquet.** A list can look beautifully mixed and still deal three roses into one tier, which is why the second rule is about the remainder and not the distance. If a template is ever edited by hand, re-run both tests over `TEMPLATES` rather than reading the lists.

- **A template is TEN stems and TWO foliages.** It was six and one, and that left every template looking like a hand of flowers rather than a bouquet somebody would send: the wrap read as mostly paper, and one foliage at the density tuned for nine stems cannot fill the gaps between them. `MAX_FLOWERS` is 12 and `MAX_FOLIAGE` is 2, so this sits near the top of what the builder itself allows, which is the point: a template must never promise something a sender could not make by hand. The two foliages are picked to be UNLIKE each other, since the mixer drops each to 0.62 density; two leafy kinds together read as one denser leafy kind.
- **FIVE presets and a sixth tile that is blank.** "Build your own" is IN the grid rather than a button underneath it, which fills three by two at every width and makes building from nothing one of the six choices rather than the thing you fall back to when none of the five fit. Its art slot is 175px to match the preset canvases, which are capped at 140 wide and painted at a fixed 5:4.
- **A template is nothing but a preset of `state`**, which is why it costs so little: every one renders through the same arrangement code as a hand built bouquet, so a template tile cannot promise something the builder would not produce.
- **Picking one lands on the LETTER step, not the reveal.** The words are the one thing a template cannot supply. Every other step is already answered and still reachable by walking back, so it is a shortcut rather than a lock.
- **`syncBuilderToState()` rebuilds every control after a template is applied**, and it deliberately does NOT call `initWrapStep`. That one binds the three sliders, which live outside the grid it clears, so calling it twice binds them twice; `refreshWrapStep` is the safe half. `initFlowerGrid`, `initFoliageGrid` and `initSwatchGrid` all clear their own container first, so re-running those is safe.
- **`markSwatch` only unlocks the Continue button once it has actually found the swatch.** Enabling it regardless would let a template naming a palette id that no longer exists walk the sender past a step with nothing chosen.
- **`buildWrap(h, s, l, pattern, ribbonHue)` was extracted out of `currentWrap()`** so the templates can describe a paper without going through `state`. Hand rolling that object at the call site got `pattern` and `ribbon` wrong on the first attempt, which is exactly the drift the extraction prevents: `currentWrap` returns `{id, name, h, s, l, pattern, ink, ribbon:{h,s,l}}`, not the `p`/`r` shorthand the template data uses.
- **The template canvas is capped at 140px wide, and that is arithmetic not taste.** `renderBouquetCanvas` takes its height from `clientWidth` at a fixed 5:4, so a 300px column paints a 375px tall bouquet and three rows of those run the card past 1300px.
- **They are painted on ARRIVAL, not at boot.** A canvas inside a step that is still `display: none` measures zero, the same rule the note previews already follow.

### The viewport meta, and why the gardens read as tiny on a phone

**Both garden pages had no `<meta name="viewport">` at all, and that single missing line was the cause of the whole complaint.** Without it a phone lays a page out at **980 CSS pixels** and then scales the result down to fit the screen. So `innerWidth` reports 980, `matchMedia("(max-width: 768px)")` reports **false**, and every phone rule in both garden stylesheets was dead code that had never once matched. The sizes in those blocks were not wrong; the page simply never admitted it was on a phone.

- **Measure this numerically, never by looking.** A page laid out at 980 and scaled down looks exactly like a page laid out at 375 with everything too small, which is precisely how it was described. `matchMedia(...).matches` is the one line that separates the two, and the browser pane's viewport emulation is itself unreliable here, so check `innerWidth` and the media query together rather than trusting either.
- **It changes what p5 measures too, and that is the risk worth knowing.** `width` went from 980 to the real device width, so every `width < 720` branch in both sketches now fires on a phone for the first time. Those branches were written for phones, so this is them finally running, but it means a phone is now taking code paths nothing had ever exercised.
- **There is deliberately NO `maximum-scale`.** The old iOS script set `maximum-scale=1`, which blocks pinch zoom and takes the page away from anyone who needs to magnify it. The only thing it bought was stopping iOS zooming in on a focused field, which the 16px floor below does without that cost. That script is deleted from both pages; it never worked anyway, since the meta it reached for was not there.

### Do not put anything above `<!DOCTYPE html>`

All four pages were briefly rendering in **quirks mode**, because a Supabase CDN tag and a `config.js` tag had been added above the doctype. Anything before the doctype makes the browser ignore it, and quirks mode silently changes layout on every page. Three of the four also loaded their own sketch a second time up there, which threw `SyntaxError: Identifier 'SPECIES' has already been declared` on both gardens and, on the personal garden, put the sketch tag back in the HTML that CLAUDE.md specifically says must not carry it.

**THE GARDEN'S NAME STARTS BELOW THE ICON ROW ON A PHONE.** Both are positioned from the top of the same screen: the four round controls sit at top 16 and are 34 tall, so they own everything down to 50, and the garden's name was placed at 18 and ran straight underneath them. The name goes to 62 and the line under it to 106, both `!important` since `buildUI()` sets the same `top` inline. The line also needs a WIDTH, not just a cap: the sketch sizes it off a formula reserving 200px either side for the Home pill and the icons, which on a 390 screen leaves 195 and wraps a sentence to four lines, and below the icons there is nothing either side to reserve for.

**The side nav is HIDDEN below 768px, not shrunk.** It was 36px circles at left 8, and on a narrow screen the copy runs the full width, so the column sat on top of the hero's paragraph and down the left edge of every section after it. What it offers is a jump between sections, which on a phone is what scrolling already is, so it was paying for itself in covered text and giving nothing back.

**The four round icons FADE WHILE THE PAGE IS MOVING and come back 550ms after it stops**, below 768px only. They are fixed over a page whose copy runs the full width, so a section title passes underneath them on the way past and is cut in half while it does; on a wide screen that never happens, because the content is narrower than the window and the corner is empty.

- **Padding the copy away from them was the other option and it is worse.** The overlap only exists for the second or two a title is level with them, and that fix would cost every phone screen 90px of width for ever.
- **It lives in `garden-cursor.js`**, which owns the chrome every page shares, as one rule keyed off `data-gg-scrolling` on the root element. The gardens do not scroll at all, so it costs those pages nothing either way.

**The page sparkles decide for THEMSELVES whether to draw, from the section's own box, every frame.** The IntersectionObserver is an optimisation and not the authority: it frees a canvas by setting it to zero when its section is far away, and if its callback was ever late, missed or never delivered, `rec.on` stayed false and that canvas stayed zero FOR GOOD, since no resize event fires to correct it. **That is how the sparkles vanished from the whole page**, with no error anywhere. `paint()` now tests the section's rect itself and the observer's flag only lets it release memory.

**`cursor: pointer` must not be set on any BOX this project draws a cursor over.** `cursor` INHERITS, so a value on `.garden-card` beat the flower and turned the pointer into the operating system's hand over a third of the landing page; `.flower-tile` had the same. Both are gone. The card is a link on a phone and the phone block is where that lives now.

**The hero's top padding is 82 on a phone, not 70.** The account and music buttons end at 52 there, and the eyebrow used to start level with them.

**The meadow shows a NARROWER SLICE of its logical scene on a small screen, it does not shrink.** It is drawn in a 1440 wide logical space and scaled to fit, so at 390 the scale was 0.27 and a bloom of radius 17 came out five pixels across. `geom.xk` then squeezes the flowers' x positions by the same ratio in `draw()`, so the row still spans the full width rather than running off the right edge, and `minSpacing` thins whichever end up too close. **`GardenLife.meadow` has to be passed `VIEW_W`, not `LOGICAL_W`**, or the butterflies and motes populate a scene half again as wide as the one on screen.

- **THE SLICE IS DERIVED UNDER 900, NOT STEPPED, and that removed two faults at once.** It was 540 under 620 and 980 under 900. The first left a phone at a scale of 0.72 with 12px blooms, still a row of specks; the second put a cliff at exactly 620 where the scale fell from 1.15 to 0.63 and every flower halved for one pixel of window. `VIEW_W = clamp(round(W / 0.95), 360, 980)` holds the scale at a constant 0.95 across the whole range, so a bloom is 27 to 44 pixels on every phone and every small tablet, which is the size the garden pages draw, and nothing jumps as the window is dragged.
- **`minSpacing` is a FRACTION of the width, 0.155, not a pixel count**, because the blooms are a constant fraction of the width too. The old fixed 104 and 88 were tuned when a phone bloom was 12px across and dropped all but three once the blooms doubled, leaving a third of the meadow bare. At 0.155 a phone keeps six of the eleven, spread from 26px to 349px of a 375 wide screen with 27px of clear ground between the closest pair. The first and last kept are both daisies, which is fine: they land at opposite ends, which is the rule the hero already follows for repeats.
- **The x positions span the full width whatever the slice, and the arithmetic is why.** `xk * scale` is `(VIEW_W/1440) * (W/VIEW_W)`, which is `W/1440` with the slice cancelled out. So changing `VIEW_W` changes only how big things are drawn, never where they sit. If the row ever ends short of the right edge, it is `minSpacing` dropping flowers, not the slice.

## `garden-cursor.js` owns the chrome every page shares

Two things live in this one file, and they are together because both are needed on all four pages and neither belongs to any one of them: the cursor, and the hover label on an icon.

### The hover labels

**Any control carrying `data-tip` gets a short label under it.** The browser's own `title` already does this, but only after a long pause and in the operating system's styling, and the top right of every page is now a row of four unlabelled icons, which is exactly where a fast legible answer to "what is this" is worth having. It is pure CSS off an attribute, so a module adds one by setting a single attribute and nothing has to be built.

- **It is CENTRED on its button**, `left: 50%` with a `translateX(-50%)`. Anchored to a corner it pointed at the gap between two icons rather than at the one it belonged to, since these are round icons in a row eight pixels apart.
- **The music button has NO label, and that is the one exception.** Its volume panel drops into exactly the space a centred label would take, and pushed to the left instead it ran across the three icons beside it. It is also the one button in the row that explains itself, since hovering it slides out a volume slider. `data-tip-side="left"` is gone with it; nothing uses it.
- **None of these buttons carries a `title` any more.** `title` and `data-tip` together meant hovering produced the project's own label and then the operating system's on top of it, which is what "don't have it doubled" was. `aria-label` is what a screen reader reads and it is enough. **Do not add a `title` to anything that has a `data-tip`.**
- **`@media (hover: none)` removes it.** A label stuck open after a tap is worse than none.

### The cursor

**A FLAT FIVE PETALLED FLOWER at rest, shrinking to a SPARKLE over anything clickable, on ALL FOUR pages.** It used to live in `bouquet-style.css` and appear on one page of four, which made that page the odd one out rather than a theme.

- **THE FLOWER IS AT REST AND THE SPARKLE IS ON A CONTROL, which is the reverse of where it started.** A solid bloom over a control sits on top of the very thing being aimed at, at the moment its hover label is opening and wanting to be read. At rest there is nothing underneath to hide, so the rose can be the size it needs to read as a rose, and the sparkle that replaces it is small and mostly empty. **Do not swap them back without solving the covering.**
- **A CURSOR CAN CARRY ABOUT SIX SHAPES. Anything past that is texture nobody can see and weight everybody pays.** This is the rule the whole history of this file comes down to. It has been the favicon's concentric scalloped rings, then a rose with a spiral centre inside three rounds of overlapping cupped petals, eighteen shapes in all. At thirty pixels that was a blue smudge, and it did not read as a rose either. **Do not add layers, shading or a spiral back.**
- **So it is one ring of five petals, one flat blue, one outline, one centre.** `flowerArt()`, and that is the whole drawing. It is what a flower looks like at icon size and it still reads at twenty, which is what the smaller of the two states needs.
- **Its blue is the favicon's**, sampled off `apple-touch-icon.png`: hue 206 at about 58 percent saturation, pushed here to 66 because an icon sits in browser chrome of its own while this has to hold against six section colours. The flower is no longer the favicon's SHAPE, only its colour.
- **The DOUBLE OUTLINE is the only thing that works on every ground, and it was measured.** No single outline colour can do it: dark teal scores 1.00 against the dark teal band and 1.35 against the dark green card, and cream scores 1.00 against cream and 1.06 against the pale blue. A near black line inside a cream halo always has one of the two separating, 13.2 on cream and 6.5 on dark teal. The sparkle carries the same treatment for the same reason.
- **EVERY halo is stroked before ANY petal is filled.** Interleaved, a later petal's cream stroke lands on top of an earlier petal's fill and cuts a pale scar across the flower.
- **206 also does something no other hue here can.** Every colour on these pages is a teal, a cream or a pastel bloom, so a saturated blue is the one thing never mistaken for the page behind it.
- **Things tried and rejected, so they are not tried again:** a leaf (the one thing in a project of flowers that was not a flower); the same flower at two sizes (on pale cream the colour barely moved and a size step that small reads as the pointer wobbling); a bud drawn as five narrow petals tucked in (overlapping ellipses at that size read as a spindly star); and a plain teal arrow, accurate and with nothing to do with the project.
- **`DEFAULT_HUE` is 206 and `apply()` now moves BOTH states.** The rose is the one you actually look at, so in the personal garden it is the rose that carries the hue of the flower planted most recently; tinting only the little sparkle would have put the personal touch on the half nobody studies.
- **The rose is 30 pixels and NOTHING HERE MAY EXCEED 32.** Windows refuses a custom cursor larger than 32 by 32 outright, and a refused cursor falls back to the plain system arrow, so anything bigger silently loses the mark on every Windows machine.
- **The FALLBACK keyword differs by state**, `auto` at rest and `pointer` on a clickable. It is what a machine that refuses to draw a custom cursor gets, and giving both the same one would leave such a machine with no signal at all.
- **It is injected from JS rather than written in a stylesheet** so the bloom can be RECOLOURED at runtime. In the personal garden it takes the hue of the flower planted most recently, so the thing following the pointer is the last thing that grew. Everywhere else it is the palette's butter yellow.
- **EVERY rule carries `!important`, and that is a fix rather than a shortcut.** This file is loaded from the head, so its style tag is the FIRST in the document, and every module that builds a control appends its own tag after it. Four of them set `cursor: pointer` on an ID (`#gj-btn`, `#gg-music-btn`, `#ga-friends-btn`, `#gj-close`), which beats an element selector outright, and both gardens set `#save-btn`'s cursor INLINE, which nothing but `!important` reaches. So the four round icons in the corner of every page kept the system arrow while everything around them drew a flower. **Adding those ids to the list would NOT have worked**: each selector in a list carries its own specificity, so `#gj-btn` there would only tie, and the module's tag comes later.
- **The class list is still load bearing.** A class rule carrying `cursor: pointer` outranks a bare `button` selector, so every clickable class in the project is named explicitly. Anything new that sets its own `cursor: pointer` has to be added there.
- **What is NOT in that list matters as much, and three entries were removed.** `.garden-card-inner` put the flower over the whole of each of the three cards, six hundred pixels of title, paragraph and small print, when the only thing to press is the button at its foot. `.flower-tile` did the same across each guide tile. `label[for]` is clickable in the technical sense and in no other. All three still work exactly as before; they just show the arrow while you read them. **The rule is that the flower marks a CONTROL, and a large box you happen to be able to click is not one.**
- **Inputs, sliders and disabled controls are declared LAST so they win**, and they carry `!important` too, so they still win by order and by specificity. A caret and a grab handle each say something true about a control that a decorative cursor would throw away.
- **`@media (hover: none)` turns the whole thing off**, since a touch screen has no cursor to draw.

## The flower guide is a RING, and the grid beside it is the fallback

**The eight blooms drawn close up and set round a circle, with a hairline running out of whichever one is under the pointer to its own name and meaning.** It is a botanical plate: the specimen in the middle and the naming off to the side on a leader line, rather than a caption sitting under a picture in a box.

- **There was briefly a display heading and a numbers band here and both are GONE.** The heading mixed an italic serif drop capital with a sans second line, and the band carried four figures about the project. They came from a reference photograph and read as another site's furniture dropped onto this one. The heading is back to `Every mood has a <em>symbolic bloom</em>` and the band and all of its CSS are deleted. **Do not bring either back**; the thing that was wanted from that reference was the annotation lines, which is what the ring is.
- **The ring is ROTATED by half a step**, so the eight sit at 22.5, 67.5, 112.5 and 157.5 degrees either side rather than on the compass points. That is not decoration: a bloom at the very top has no side to put a label on, and one at the far left has no room above or below it. Off the axes every one of the eight has an unambiguous side and a clear run out to it.
- **Nothing in the geometry is a percentage.** A label's own measured width is the budget the ring lives inside, so `layoutRing` reads `offsetWidth` back and sizes the ring to what is left. The bloom's size and the radius each depend on the other, so it is solved in two passes rather than guessed.
- **The stage's height is measured, not set.** It comes out of the extreme label and bloom positions, so a long meaning can never run out of the section it annotates.
- **The ring IS A COLOUR WHEEL, and the hues were moved to make it one.** It used to carry the rose, the lotus and the sakura all at hue 340, three flowers in one pink sitting side by side, with a 140 degree jump from the sunflower straight to the lily. None of the eight sits on a compass point either, which is what gives every one a side to put its label on.

Its saturation is held down to 34, or it stops reading as a bloom and starts reading as a leaf. **Its position moved with its colour**, from beside the rose at the top to between the sunflower and the lily, which is where a green belongs on a wheel and is also the one stretch that had nothing in it.

- **The blooms are `Rr * 0.85`, floored at 118 and capped at 176.** The chord between two neighbours is 0.765 of the radius and a bloom paints about four fifths of its square, so at this factor there is still air between them: measured at radius 140 the chord is 107 against painted blooms of 95.

The tulip was 280, four degrees off the lavender's 270, so the ring carried the same purple twice side by side; it is 232, between the lavender and the lily and still on the violet side of blue. The daisy was 55, three degrees off the sunflower's 45 with the same yellow; it is 22, between the sakura and the sunflower, which makes it the ring's one apricot. **The bouquet's own `SPECIES` palette is separate and was NOT touched**, since a hue there is the default for every bouquet ever built.
- **THE HEADING SITS ON TOP, like every other section's, and that is settled.** It was in the middle of the ring for a while. Distinctive, and wrong: all five other sections open with an eyebrow and a title near the top, landing within 75px of each other, so the flower guide hiding its title inside its content was the one section announcing itself differently and it read as belonging to another site. It cost as well, because type in the middle needs a wide empty circle, a wide circle needs a big radius, and a big radius made the section a screen and a third. **Do not put it back without re-reading this.**
- **Every bloom's ORIGIN in the ring is placed by MEASUREMENT, not by the catalogue tiles' numbers.** Where a species' origin goes is not where its middle ends up: each paints a different amount above and below it, and the lavender and the lotus grow upward out of an origin their own drawing pushes down. Painted and read back, the vertical centre landed at 0.519 of the slot for most of them, 0.635 for the tulip, 0.622 for the lavender and 0.461 for the lotus, against a middle of 0.5, which is the tulip sitting an eighth of its box low beside the lily. Each origin is shifted by its own error and all eight now land within 0.001. **Re-measure if any species' drawing changes.**

Without it they read as eight flowers that happen to be scattered; with it the arrangement is plainly a diagram, which is what the labels are already pretending to be. It is the ruling on the page rather than a thing to look at: 1px, `rgba(66,146,136,0.30)`, dashed 2 on 7.

## The loading flower (`garden-loader.js`)

**One bloom opening over the garden's own sky, on ALL FOUR pages.** The stem rises, the leaves unfold, six petals open one after another, the eye fills in, and it loops every two and a half seconds.

- **The shared garden is what needed it.** That page has to reach a websocket on somebody else's server and load a room before it can draw anything, and until it does there is a blank screen with no way of telling a slow connection from a broken page. The other three are quick, but **a loader that appears on one page of four reads as that page being the broken one**, so all four carry it.
- **Nothing in it is p5.** The gardens' flower code lives inside their sketches, and the sketch is precisely what has not loaded at the moment this has to draw. The bloom is drawn on a raw canvas and is deliberately NOT one of the eight: a loader showing a daisy would be promising a daisy.
- **Two ways out and both are needed.** `done()` is called by a page that has something to show, and a **CAP** hides it after 9 seconds whatever happens. A loader that can outlive its page is worse than none, because a failed connection would leave a flower turning over nothing for ever.
- **`hold()` must be called before the window's load event**, and it only works because both callers' script tags sit AFTER `garden-loader.js` in the head. Move either above it and the hold silently does nothing. The shared garden holds at the top of its sketch and releases from `draw()` on the first frame that has a room behind it; the personal garden holds in its auth module and releases from whichever arrives, the sign in gate or the garden.
- **There is a MINIMUM of 550ms.** A loader that flashes for 80ms reads as the page glitching rather than as the page loading.
- **It is skipped for the rest of the session**, under `gg_loaded` in `sessionStorage`. The wait is real the first time, when the fonts, the sketch and the room are all cold; walking from the bouquet back to the landing page is instant, and a loader over an instant page is a flicker.

## The hero's sky

**FIVE clouds in two speed groups, and the timings were searched rather than picked.** A cloud "arrives" when it crosses the left edge. With the old three, at 22, 30 and 25 seconds, the longest stretch with no arrival at all was **22 seconds**: the sky emptied on the left and the next cloud only turned up once the others had gone.

- **Even spacing needs a shared period**, since arrivals from clouds of unrelated periods drift in and out of phase; searching six clouds on six different periods never got the worst gap below 13 seconds. But one shared period means one speed, and clouds that never overtake each other read as printed on a sheet. **Two groups is the compromise**: three at 24s spread a third of a cycle apart give an arrival every 8s on their own, and two at 33s cross more slowly over the top of them. Worst stretch with no arrival: 8 seconds.
- **The negative `animation-delay` is what fills the sky on the first frame** rather than over the first half minute.

**The birds have their OWN canvas, `#hero-sky`, and the block that paints it was once LOST.** When the page's single fixed dust canvas was split into one per section, the canvas stayed in the markup and nothing called `GardenLife.sky` on it any more, so the hero had no birds at all for several commits. **If they ever vanish again, check that something still paints that element** before looking anywhere else.

- **The band is 8 to 30 percent of the hero's height**, where the clouds sit between 7 and 22 percent and stand about 90px tall, so the birds fly among them rather than above the flowers. The meadow canvas cannot hold them: it begins where the meadow does, well below the copy.
- **The SHARED GARDEN pins its birds left to right**, `dir: 1`. Everywhere else the direction alternates each crossing so the flock does not always come from the same side; that garden's sky is read alongside a meadow that fills from the left as the day goes on, so the two now move the same way.
- **The HERO pins its birds left to right too**, `dir: 1`, and its gap is 1. Alternating meant every other pass entered from the side the eye had just stopped watching, which reads as the flock having been away twice as long as it was.
- **`gap` is 1 against the gardens' 22, and `nBird` is 5 against the old 3.** A visitor reads the top of a page for a few seconds and then scrolls, so a flock away for twenty two of every fifty two seconds is one most people never see; at 22 across and 1 clear there is nearly always something in the air. A skein of three reads as three dots, five reads as a flock. `nBird` is shared with both gardens, which get the larger skein too.

## The wiggling words

**Two words in the hero spring letter by letter, once on arrival and again when the pointer crosses them.** A word carrying `data-wiggle` is split by script into one span per letter, because a whole word animating tips over as a block, which reads as a wobble; letters going in sequence read as something alive.

- **Which words is a SELECTOR, not a list.** `[data-wiggle], .section-title em`. Every section title already italicises the one word it turns on, so that em is the emphasis and no new markup is needed to say so; a section added later gets it for free and cannot be forgotten. The hero's two carry `data-wiggle` explicitly because neither is a section title. Seven words in all: Gratitude, bloom, places, give, symbolic bloom, tips, waiting.
- **Only the words ON SCREEN at load run by themselves.** In practice that is the hero's two. Firing all seven in a chain would spend four seconds animating headings nobody has scrolled to, each finishing long before it was seen. The rest wait for the pointer, which is the only moment they have an audience.
- **`.wig` is `display: inline`, and each WORD inside it is a `.ww` nowrap inline-block.** Both halves are load bearing. As an inline-block the whole emphasis became one unbreakable box and a two word phrase overflowed a phone. As plain inline with no word boxes, every letter is its own box and the browser broke lines BETWEEN LETTERS: "symbolic bloom" came out as "symbolic bloo" with the "m" on the next line, and so did "waiting" and "places". The splitter now divides on spaces first, so a break can only happen where a break belongs.
- **The three verbs in "Reflect, share, give" all move.** That title is the page's summary of itself, so it is the one place where the whole line is the emphasis, not just the em. The first two carry `data-wiggle`; `give` needs nothing, being an em in a section title.
- **`.wig` is in the cursor's clickable list.** Those words are not links, but they answer when the pointer crosses them, and the bloom is what says so before you find out by accident.
- **It is NOT a loop.** A headline that never stops moving is a headline nobody reads, and on a page whose subject is slowing down it would be the one thing on screen refusing to.
- **Punctuation is left out of the sequence.** A comma flying up on its own detaches from the word it belongs to. It keeps its own span so the spacing does not shift.
- **Only the LAST letter's `animationend` clears the class.** Every letter fires its own, so clearing on the first killed the other eight part way through and the word collapsed instead of finishing.
- **Re-running needs a forced reflow** between removing the class and adding it back, or the browser coalesces the two and nothing replays.
- The stagger is 38ms a letter and the keyframes peak at `-0.22em` and -5 degrees at 28 percent, then settle through two smaller overshoots. One overshoot alone reads as a bounce off a floor.

## The landing page sparkles are per SECTION, not per page

**One canvas inside each section at `z-index: -1`, and that value is the only one that works.** It paints above the section's own background colour and below everything in it. A single fixed canvas cannot reach that gap: in front of the sections it covers the cards, behind them the backgrounds hide it. This is what "the sparkles look weird above the containers" was.

- **The hero is deliberately excluded.** It already carries birds, butterflies and its own motes on the meadow canvas.
- **`position: sticky` with `margin-bottom: -100vh`**, so the backing store is one viewport rather than one whole section. On a 7500px page that is the difference between a few megabytes and tens of them.
- **The canvas is the section's FIRST child, and it must be.** It is sticky, so where it sits in the flow is where it rests before it sticks, and appended last that was the foot of the section. Each canvas therefore covered the bottom viewport of its section and only the sliver of the band that happened to overlap it ever drew: measured at THREE motes on screen where there should have been a dozen, which is exactly why the sparkles looked like they had gone. As the first child it rests at the section's top, sticks through it, and the negative bottom margin pulls the real content back up over it.
- **`.section-dust` carries `grid-column: 1 / -1; grid-row: 1`, for `.about` alone.** That section is a grid, so its canvas is a grid item and was being dealt into a cell: 561px wide in one column instead of 1190 across the section, plus an implicit row added to the layout. On the five block sections those two lines do nothing.
- **The count is one mote per 95px of section**, which works out at about nine on screen at a time whatever the section's height, since the canvas is one viewport tall. It was one per 62, roughly fourteen.
- **An IntersectionObserver frees the canvas of any section that is not near the viewport**, so two or three are allocated at a time rather than six.
- **None of these sections may gain a `transform`, `filter` or `opacity`.** Any of those makes the section a stacking context, which traps `z-index: -1` inside it and paints the canvas behind the background after all. The same rule already protects the flower modal.
- **`GardenLife.drift` takes `opts.only`** to draw a single band. The FULL band list is still passed every time, so the population signature does not change from one canvas to the next and nothing is re-seeded per section.
- **Butterflies keep to the MARGINS**, alternating sides, with a swing tied to the page's width rather than a pixel count. The copy sits in a centred block, so the outer sixth on each side is dependably empty. One hovering over a paragraph is something a reader has to look past.

## The history (`garden-journal.js`)

**A week strip, seven days across, with the flower planted that day drawn under each one.** One file at the repo root, loaded by both gardens, and the two need very different things from it. That difference is the whole design.

**It is called HISTORY on screen, and the file keeps its old name.** It was Journal, and that word was already taken: the personal garden asks for a journal ENTRY on the day it plants, so one word named both the thing you write and the record of every day you wrote one. The button, its `aria-label`, its hover tip and the panel heading all say History. The file is still `garden-journal.js` and the global is still `GardenJournal`, because every page loads it by that name and renaming it would break four script tags for a word.

| | where a past day comes from |
|---|---|
| personal | NOTHING new is stored. Every flower already carries its date, mood, shaper and journal entry, and that array already syncs to the account, so the log is a VIEW of data the garden has always had. |
| shared | everything has to be written down as it happens. |

- **p5.party does not keep a room once its date has passed.** Checked before building anything for it: loading four past room keys returns objects with no `flowers` in them at all. So the shared side writes two things when a flower is planted. A row in `garden_entries`, which is yours alone and draws your icon in the strip. And a snapshot of the whole meadow in `shared_days`, which is public and is what a past day replays from.
- **The snapshot is throttled to once a minute** and only written by somebody signed in, because the garden redraws sixty times a second and the room changes far less often than that.
- **A day with no snapshot says so.** The garden is only remembered from the day somebody signed in was standing in it, and the panel tells you that rather than showing an empty meadow as if nothing had been planted.
- **Neither garden needs an account for the strip to work.** Without one both fall back to this browser's storage, and only the whole-meadow replay is missing.
- **Three sources are merged on read, in order of how much they can be trusted**: the garden's own data first, then the account, then this browser.
- **The shared garden hands over the ROOM as its first source, and that is what makes today's icon right.** It had no `entries()` at all, so the strip could only show what this browser happened to have written down when the flower was planted. Plant on a phone and open the history on a laptop, or plant at all before any of this was written, and today's slot was empty or holding something stale. `entries()` now reads today's flower straight out of `shared.flowers`, matched on the name it was planted under, and because it is the most trusted of the three it outranks both the note and the account row. The flower standing in the meadow under your name is the one that was planted, whatever anything else says.
- **`myPlantedName()` is the typed name if this visit planted it, otherwise the account's username**, since a signed in person always plants as their username and cannot edit it.
- **The icon is drawn by each garden's OWN preview family**, through a `p5.Graphics` whose canvas is blitted into the small DOM canvas the strip holds. An eighth copy of the flower maths would drift from the seven that already exist. The two call it differently and that matters: `drawPreviewFlower` centres itself, `drawPreviewBloom` draws around the ORIGIN and leaves centring to its caller. Missing that gave a strip of quarter flowers tucked into the top left corner of every slot.
- **The buffer is SQUARE**, because the slot is square and a tall buffer squashed into it stretches every bloom sideways. The shared garden's is **76**, and every step down to it was measured by painting all eight species and reading back the bounding box. This garden's preview draws at a fixed `baseR` of 30, so the buffer's size is the only thing that decides how much of the slot a bloom fills:

  | buffer | tallest | shortest | clipped |
  |---|---|---|---|
  | 96 | 69% | 51% | none |
  | 84 | 79% | 58% | none |
  | 76 | 87% | 64% | none |
  | 70 | 94% | 70% | none |
  | 64 | 100% | 77% | sunflower, sakura, lavender |

  76 is the last size where the widest species still has air around it. Below it the sunflower touches two edges and the lavender runs off the top, and an icon cut off at the edge of its slot reads as broken rather than as large.
- **Everything works in YYYY-MM-DD** so days sort as strings. The personal garden stores MM/DD/YYYY on every flower, which is what its labels print, so `fromUS` is the one conversion.
- **A day in the future is disabled, not empty.** It has not happened; it is not a blank page.
### The book opens on a MONTH, and a day is a page you turn to

**The week strip is gone.** `garden-journal.js` now has two views of one book, set on the panel as `data-view`:

- **month**, what the History icon opens: the month's name between two arrows, the days of the week, and a seven across grid where each day shows the flower planted on it. A day with nothing is a pale empty ring, a day still to come a faint filled circle (and disabled), today's number sits in a dark teal pill, and days from the months either side are blank. The foot counts the month's flowers.
- **day**, what tapping a day or a flower card's "Read this day" opens: a "Month" link back, the date written out, the entry, and Earlier and Later entry along the foot, which still skip to days that hold something.
- **Every icon is fitted to one size by `paintFitted`**: the garden's own `paint` draws into a spare canvas, the painted pixels are measured, and exactly that box is drawn at 84 percent of the slot. Without it a month of species read as flowers of different sizes rather than as days.
- `open()` is this month; `openAt(day)` is that day's page. Several notes below describe the strip, the week and "the calendar is the header"; the month replaces all of that, and the rest (one fixed height, the photo, the lightbox exemptions, the shared meadow replay) is unchanged.

### The panel is a BOOK in the middle, and there is only one of it

**It is one reading view with two ways in**, and that is the whole design rather than a style choice. It used to slide in from the left. Tapping a flower is what changed that: a flower can be anywhere in the garden and a side panel always arrived in the same corner, so the thing you asked about and the answer were nowhere near each other. Centred, the answer arrives where you are looking, and the garden dims behind a veil rather than being shoved aside.

- **NOTHING MAY SHOW A DAY TWICE.** The book replaced the side panel outright on BOTH gardens, and the personal garden's hover box was cut down to a glance in the same pass, because between them the three would have printed one day's entry in three places. That constraint is the reason for every decision below; if something new wants to show a day, it opens the book.
- **The personal garden's hover box is species, meaning, date, and "Tap to read the day".** It used to carry the mood, what shaped the day and the whole journal entry, which is exactly what the book opens with. The long version had a second cost besides the doubling: a paragraph of journal made the box taller than the flower it belonged to and it covered its neighbours.
- **`drawHoverTooltip` returns early while the book is open.** The veil takes pointer events, so a hover can no longer be updated once the book is up, but the last flower the pointer crossed stays in `hoveredFlower` and its box would go on being painted underneath.
- **`mousePressed` in the personal sketch has three guards and each is load bearing.** p5 calls it for a press ANYWHERE in the window rather than only on its canvas, so without the target test it fires while somebody is pressing a button on a prompt card; it is gated on the garden step, since on the prompt screens the canvas is behind a card; and it re-runs `checkHover` from the press position rather than trusting `hoveredFlower`, because a touch screen never fires a move first.
- **The SHARED garden's flower tap is NOT this.** There a tap opens the likes and comments panel and always has. Only its History icon opens the book.
- **`openAt(day)` takes YYYY-MM-DD**, sets the chosen day and the week around it, then opens. `open()` is still today.
- **THE CALENDAR IS THE HEADER, and there is no date line and no panel title.** The strip already names the day in the cell it highlights, so printing "Sunday, September 13" over a calendar with the 13th ringed is the same fact twice in one square inch. The month carries the part the strip cannot show, in FULL, since it is the one word on that row and an abbreviation saves nothing; a week straddling two months names both, or it claims to be a September the second half of it is not in.
- **The page turn moved to the foot and is WORDED, not chevrons.** "Earlier entry" and "Later entry". The header already carries a pair of bare chevrons for the week, and two unlabelled pairs in one small panel is a guess about which moves what. They still skip to days that hold an entry rather than stepping through the calendar.
- **The page turn skips to the previous and next day that HAS an entry**, never through the calendar: a diary of one flower a day is mostly empty days and turning through those is turning through nothing. It is disabled at each end so the book cannot be turned to a blank, and from an empty day it steps to the nearest real one in that direction rather than refusing to move. The calendar lives in the week strip, which was kept because it is what makes the thing read as a diary.
- **The strip moved to the FOOT.** It is the ribbon along the bottom of a diary, an index you glance at, and the page itself is what you came for. It was at the top, above the entry, which made the index the first thing read.
- **The spine is a `::before` and `::after` on the panel, not a child**, so nothing in the layout has to know about it and the scrolling body slides under it cleanly. Every row is padded past it by hand.
- **The phone block is LAST in the CSS string and has to be.** It was written higher up first and did nothing: a later rule beats an earlier one at equal specificity, so the date stayed at 19px and went on wrapping. That is the fourth stylesheet in this project to hit that trap. "Sunday, September 13" at 19px measures about 185px against about 181px of room between the two page arrows on a 375 screen, which is why it wraps and why 16.5 fixes it. Measured, not guessed.
- The button is still slot 3 of the top right row, and the veil sits at 535 with the panel at 540, above the garden and below nothing that matters.

### Photos on an entry

**A personal garden entry can carry ONE photograph, and it needs an account.** It is the one part of the journal that is not a view of data the garden already had, so it is also the one part that cannot fall back to this browser: a photo is far too large for `localStorage` and there is nowhere else to put it. The control is BUILT on the journal step either way and simply DISABLED when signed out, rather than hidden, so the feature is discoverable and the reason it is unavailable is on screen.

- **It lives in `garden-journal.js`, not in the sketch.** `uploadPhoto(day, file)` and `photoUrl(path)` are exported on `window.GardenJournal`; the personal sketch owns only the file input, the thumbnail and the call. The journal already owns every other per-day fact, and splitting the photo across two files would put half of a day's record in each.
- **The bucket is PRIVATE and the URLs are SIGNED, which has a consequence worth knowing.** `createSignedUrl(path, 3600)` means a link copied out of the page stops working within the hour. That is the point, but it also means a URL cannot be stored anywhere: only the PATH goes in the `photo` column, and the signed URL is derived on read and cached in memory for the life of the page.
- **The path is `<uid>/<day>.<ext>` and the policies key on the first segment**, `auth.uid()::text = (storage.foldername(name))[1]`. So the shape of the path is what enforces the privacy, not a check in the page. Do not flatten it.
- **The extension is sanitised before it reaches the path.** Anything over five characters or carrying a character outside `a-z0-9` becomes `jpg`. A file name arrives from the visitor's own disk and goes straight into a storage key.
- **`upsert: true`, because a day has one photo.** Replanting or re-picking on the same day overwrites rather than accumulating, which matches how every other field on a day behaves.
- **Every failure returns an empty string rather than throwing.** An upload that fails must not take the flower down with it: the flower is the thing being planted and the photo is an extra on it.
- **The frame is inserted before the URL arrives.** `drawDetail` puts an empty `.gj-shot` in immediately and fills it when the signed URL resolves, so the panel does not reflow under somebody reading it.
- **THE PHOTO IS A 128px SQUARE AT THE FOOT OF THE PAGE, and it fills rather than letterboxes.** It began as a full width 4:3 frame about 320px tall, which made it by far the largest thing on the page. A square that letterboxes is a square with a picture floating in the middle of it, which is worse than either shape; a square that fills is a thumbnail, which is what this is. Cropping costs nothing HERE ONLY BECAUSE the whole picture is one tap away, so do not carry `cover` over to anywhere that has no full size view.
- **The page reads answers, then writing, then picture**: species, meaning, `Mood`, `Shaped by`, the entry, the photograph. The two one word facts are labels on the day and belong with the species above them; the sentence is the day itself and wants a clear run rather than being wedged between a photograph and a pair of fields.
- **Its badge is an ICON, not a worded chip.** "Tap to open" does not fit across a 56px stamp, and a label cut in half says less than no label. The words stay in the button's `aria-label`.
- **ONE SIZE, ALWAYS: `height: min(86vh, 520px)`.** A floor was tried first and was not enough. At `min-height` a day with a photo still measured 496 against 408 for a day with two lines, so turning a page changed the size of the thing being read and the book moved under the hand turning it. A fixed height is what a book has: the covers do not grow for a longer chapter. A short day carries empty page under the writing, which is what the foot of a diary page looks like anyway, and a long one scrolls inside.
- **520 was MEASURED, not picked.** The tallest ordinary day, species and meaning, the two fields, a two line entry and the 128px photograph, comes to 322px of page. At the first attempt of 470 the body held 278 and the photograph sat 23px under the fold, so every day with a picture had to be scrolled to see it. Re-measure this if anything is added to the page.
- **A TAP ON THE FULL SIZE PHOTO'S SURROUND IS NOT A TAP OUTSIDE THE BOOK.** The viewer is appended to `document.body` rather than to the panel, because it has to sit above the veil, so the panel's own dismiss rule counted a tap on its dark surround as a tap away from the book and shut both: one tap, and the entry you were reading was gone with the photo. Both dismiss paths now check the viewer first. Escape belongs to the photo while it is up and to the book afterwards, so a press closes one thing at a time. **Anything else that appends to the body while the book is open needs the same exemption.**
- **The frame is `object-fit: contain`, NOT `cover`, and that was a real fault.** A fixed 4:3 box cropping to fill turned a portrait photo into a strip through its middle; on a phone screenshot, which is the obvious thing somebody keeps with a day, that is most of the picture gone with no way to get it back. It letterboxes on a pale ground now, so whatever shape the photo is, all of it is in the panel.
- **`.gj-shot` is a real `<button>`, and tapping it opens the photo full size.** A 300px column shows a thumbnail whatever the fit, so there had to be a way to actually look at the thing. It is a `<button>` rather than a div so a keyboard reaches it and so the project's own cursor already treats it as something to press, since `button` is in the clickable list. It stays `disabled` until the picture has arrived, which is also what keeps the "Tap to open" chip honest.
- **The full size view is built and torn down per open, never kept in the document.** A signed URL expires within the hour, so one left lying in the markup is a broken picture waiting to happen. It closes on Escape, on a tap anywhere that is not the photo, on its own close button, and with the panel, since it is appended to `document.body` and would otherwise hang over a closed panel. All five were checked.
- **The control carries a GALLERY icon, not a camera, and keeps its words.** The input is `accept="image/*"` with no `capture`, so a phone offers the camera and the camera roll both; a camera icon would promise only the first. The label stays because an unlabelled dashed box in the middle of a form is a guess, and this is the one control on that step nobody is looking for. `createButton` writes its argument as innerHTML, which is what lets the icon be inline SVG rather than a file; the button needs `display: inline-flex` or the icon sits on the text's baseline and rides high.
- **It needs Step 8 of `SUPABASE-SETUP.md`**, which adds the `photo` column, the private `entries` bucket and four storage policies. Without it the column query fails the way every other missing column does here, with a 400 and an error object rather than a throw.

**Every tip is a FRAGMENT of about five words, not a sentence.** This card sits in the corner of a garden somebody is looking at, so it has to be read at a glance rather than studied. They were full sentences running to eleven and twelve words, which is a paragraph in that corner.

**A tip is also only worth its line if it names something the visitor would not otherwise find**, and both lists were rewritten against that. Two of the shared garden's four had gone stale outright: Save PNG is a camera in the row of icons now, and nothing anywhere said that a flower can be liked, replied to, or looked back at by the day. Both now end on the same line naming the four icons in the corner, since that row is where everything added this year lives and an unlabelled icon is exactly what a tips card is for. The personal garden's third line is still conditional on being signed in, and says where the garden is saved.

## The shared garden's daily note

**`#daily-note`, the line that says the day is done, and it is the personal garden's line brought across.** Arriving straight in the garden with the planting steps gone says nothing about WHY they are gone, and the only reading left is that something failed.

- **It sits on the SAME ROW as the four round icons**, not under them. They are 38px tall at top 20, so the box takes that exact height and centres its line inside it with flex, which puts the line level with the icons instead of floating in the sky below them. Its own top is **30, not 20**: level to the pixel read as slightly high, because the icons are 38px circles and this is a single line of 15px text, and a circle's visual mass sits lower than its box. Ten pixels down is where the two look level. The icons occupy the right 192px and the Home link the left 120, so 200 either side is the clear middle; the 260 floor stops the box collapsing on a phone, where those controls are smaller anyway. Measured at 1100: the note ends at 824 and the nearest icon starts at 908.

## No white text shadow on either garden

**`text-shadow: 1px 1px 0 rgba(255,255,255,0.6)` is gone from the personal garden's title and both gardens' daily notes.** A white shadow under dark green or teal text on a pale sky is not a lift, it is a halo: it fattens every letter by a pixel on two sides and reads as print that has not quite registered. Both grounds are pale enough that the text already has its contrast, which is the only thing a shadow there could have been buying. **Do not add one back to make text "pop" on the sky.**

### One flower a day in the shared garden

**Two checks, because neither is enough alone.** The ROOM is the honest one: today's flowers are in `shared.flowers`, so a name that has already planted is visible to everybody and cannot be hidden by clearing anything. The BROWSER marker catches the same person typing a fresh name, which the room cannot see.

- **Neither is airtight, and that is the accepted cost of a garden anyone can plant in without an account.** Somebody determined can clear their storage and type a new name. Requiring an account to plant was considered and turned down, because being able to try the page in ten seconds is the point of it.

- **When it is blocked, Continue becomes "See today's garden"** rather than a dead button.
- **Already planted today goes STRAIGHT to the garden at boot.** Asking somebody what they are grateful for, letting them type it, and only then telling them they have already answered is the wrong order to find that out in. The boot check is the BROWSER marker, since `username` is empty at that point; the account's name is checked when it resolves, and only while the landing step is still untouched so nobody is pulled out of a sentence they are part way through.

## Sound

**`garden-music.js` at the repo root is loaded by ALL FOUR pages, and there is deliberately only one copy.** This project already pays for the same flower maths living in seven places; a second audio engine would drift the same way within a session. The page names its mood on the script tag itself, which is how one shared file tells four pages apart without any of them setting a global first:

```html
<script src="../garden-music.js" data-mood="calm"></script>
```

| page | mood | key | what makes it that mood |
|---|---|---|---|
| `index.html` | `whimsy` | F Lydian | the raised fourth, which never quite settles |
| personal garden | `calm` | D major pentatonic | the slowest, lowest and darkest of the four |
| shared garden | `bright` | G major pentatonic | four times the note density, and it climbs rather than wanders |
| bouquet | `romantic` | Eb major sevenths | the only sawtooth pad, plus a bass and a slow vibrato |

**Nothing is downloaded and there are no audio files in the repo.** Every note is synthesised by the Web Audio API as it plays, which is also why it never audibly loops: a clip repeats every thirty seconds and you start waiting for the join, while this only ever repeats its chord cycle. The reverb is a generated noise tail through a `ConvolverNode`, not a recorded room, for the same reason.

- **`MOODS` is the whole design surface.** Root, scale, chords, note rate, waveform, filter and reverb. All four progressions are I - vi - IV - V in some dress, because that shape resolves forever without ever asking for a cadence, and every `scale` is pentatonic or close to it, which is what lets a randomly chosen melody note never clash with the chord under it.
- **Each mood carries a `trim`, and the numbers are measured rather than chosen.** Four patches built from different waveforms do not arrive at the same loudness on their own. Untrimmed at the master output they ran calm 0.0426, whimsy 0.0270, bright 0.0193 and romantic 0.0187 RMS, a spread of about 7dB, which is plainly audible as a jump when you walk from the personal garden to the bouquet. **Re-measure and reset them if you change a mood's waveform, gain or note density.**
- **The trims were RE-MEASURED and they moved, so treat the current four as measurements rather than as settled values.** They are whimsy 0.98, calm 0.64, bright 1.27, romantic 1.66, and they were 1.00, 0.66, 1.45 and 1.50. The first pass matched the four over one long window, and what anybody actually hears is the first few seconds of a page. Measured two ways, over 32 seconds and again over just the eight seconds after the fade-in, the old trims came out at a **1.85dB** spread across the whole piece and **2.25dB** across the opening, the shared garden loudest and the bouquet quietest. Trimming against the MEAN of the two windows gives **0.60dB and 0.71dB**, both under the step anyone notices.
- **The opening matters more than the average, because the four fill up at different rates.** `noteSecs` runs 0.5 in the shared garden against 1.3 in the bouquet, so the bouquet is still arriving while the shared garden is already at full density. A trim fitted to the long window therefore lands the bouquet quiet exactly where somebody is deciding whether the page has sound at all.
- **The measurement is an OFFLINE render, not a listen.** Each mood goes through an `OfflineAudioContext` with `Math.random` seeded identically, which is what makes two moods comparable at all: the melody, the note gate and the reverb noise are all random, so an unseeded pair differs by more than the trims do. The harness pulls `MOODS` and every voice function out of `garden-music.js` **as text** and evaluates them, rather than holding its own copy, so it cannot drift from what the pages play. It is a throwaway file at the repo root, deleted after use. Peaks were checked alongside: the loudest is 0.155, so nothing is near clipping and a trim can be raised.
- **The slider position was never the problem and does not need changing.** `gg_music_vol` is one key on one origin and all four pages read it with the same 0.5 default, so the position is already shared. What differed was the patch behind it.
- **A sawtooth needs a much lower filter than a triangle to sound equally warm.** Romantic first measured a 467Hz spectral centroid against whimsy's 358, so the warmest mood was the second brightest. Its cutoff went 620 to 520 and its bell shimmer 0.26 to 0.20, which brought it to 432. Whimsy gets to 358 on a triangle at a 1500 cutoff, because a triangle has almost no harmonics to filter in the first place.
- **The scheduler queues notes against the AUDIO clock, never plays them from the timer.** `setTimeout` is nowhere near accurate enough to place a note. It only ever wakes up, looks `LOOKAHEAD` seconds forward and books whatever falls in that window.
- **Chords and melody run on two independent clocks, not one grid.** The melody drifts across the chord changes rather than landing on them, which is what stops it sounding like a sequence.
- **Stopping SUSPENDS the context, and it has to.** A suspended context freezes `currentTime`. Left running while silent, a hidden tab throttles the timer, the clock runs on, and the next wake-up finds every missed chord in the past and fires them all at once. `start()` also re-bases both clocks for the same reason.
- **The arming listeners must survive a gesture that did not unlock audio.** Browsers refuse to make sound before the visitor interacts, so the engine waits for a first gesture. A scroll or a wheel is NOT a user activation in Chrome, and this page is one people scroll, so removing the listeners just because one fired would spend the only chance on a gesture that was never allowed to unlock anything. They come off in `unarm()` once `ctx.state === "running"` and not before.
- **The music button owns `top: 20px; right: 16px` on every page**, 38px, z-index 260, which puts it above the gardens' Home link at 200 and below the landing page's flower modal at 300 and the bouquet's card modal at 900. It is built in JS against `document.body` with its own injected `<style>`, so adding it to a page is one script tag and nothing else.
- **Save PNG used to hold that exact spot on both gardens and was moved to `right: 66px`**, which leaves a 12px gap, measured. That is **three** places, because the personal garden sets it inline and in CSS and inline wins: `personal-garden-sketch.js` `saveBtn.style("right", ...)`, `personal-garden-style.css` `#save-btn`, and `shared-garden-style.css` `#save-btn`. The dead rule was moved with the live one so it cannot resurface with the old value.
- **The volume panel drops BELOW the button rather than sliding out beside it.** Sideways is the obvious direction and it would open straight onto Save PNG, which sits immediately to the left on both gardens.
- **The panel is a transparent wrapper with a `.pill` inside it, and that is the fix for a real bug, not decoration.** It first sat at `top: 44px` under a 38px button, which left a 6px gap belonging to neither element: `#gg-music` is only as tall as the button, so the moment the pointer entered that gap the hover was lost and the panel closed under the hand reaching for it. The wrapper is now `top: 100%` with a transparent `padding-top`, so the gap is INSIDE the panel and the hit area runs unbroken from button to slider while the gap still reads as a gap. Verified by walking a pointer down the centre: all 69 pixels hit test inside the control, zero breaks. Closing also carries a 350ms `transition-delay` so clipping a corner does not dismiss it, and it uses `visibility` rather than `pointer-events` because visibility transitions reliably with a delay and also keeps the slider out of the tab order while shut.
- **The slider input is 16px tall against a 4px visible track.** The track is styled through `::-webkit-slider-runnable-track` and `::-moz-range-track` so the grab area is the whole height of the pill's inside rather than the hairline you can see. At 4px it was accurate to about a pixel.
- **Bells are the only voice that creates a `StereoPannerNode`**, which makes panner count an exact note count. That is how the note densities above were measured, and it is much easier than trying to pick attacks out of the waveform.
- **Music is ON by default**, and always was: `wantOn` reads `gg_music_on` with a default of `"1"`. Nothing had to change for that. What was missing was TELLING anyone, which is what the hint below does.
- **The hint may only appear once the music is actually PLAYING.** It says so in words, so announcing it on load would be a claim the page cannot keep: audio does not start until the visitor's first gesture, and a scroll or a wheel is not a user activation in Chrome, so that gesture may be one the browser refuses to unlock sound on. `showHint()` is therefore called from the one place that already knows the context is genuinely running, which is the same place `unarm()` is called, both branches of it.
- **Once a VISIT, not once ever and not once a page.** `sessionStorage` under `gg_music_hint`, so walking between the four pages does not say it four times and a later visit is a new visitor as far as this is concerned. Anyone who has already muted is never told, since they plainly know how, and using the button at all marks it seen.
- **The hint hangs off the button, in the volume panel's corner, and that is deliberate.** It is pointing AT the button, so it has to come from the button. They cannot both be open: `pointerenter` on `#gg-music` dismisses the hint, since reaching for the control means it has done its job. It also goes on click and after 7 seconds.
- **The notch is two rotated squares, not one.** A single bordered square shows its own lower edges through the panel it is supposed to be part of, so the back one carries the border colour and the front one, 2px lower, carries the fill.
- Local keys, shared by all four pages since they are one origin: `gg_music_on` ("1"/"0") and `gg_music_vol` (0 to 1). The hint's marker is in `sessionStorage`, not here, because it is meant to come back.
- Everything is under one master gain, so a fade is a single ramp and there is exactly one place the volume lives. `MAX_GAIN` is 0.34, deliberately low: at the top of the slider this is still background music.

## Accounts, usernames and friends (`garden-account.js`)

**One file at the repo root, loaded by BOTH gardens, and it owns the only Supabase client on the page.** Two clients both watch the same stored session and both try to refresh it, and worse, the pages would drift apart on what a signed in person is called. `personal-garden-auth.js` and `shared-garden-social.js` both call `GardenAccount.client()` and fall back to making their own only if this file is not there.

It owns four things: the client and session, the profile row, the username, and friends. It deliberately does NOT own the personal garden's sign in gate or its `GardenStore`, nor the shared garden's comment panel.

- **A username is claimed on a screen of its own after the first sign in**, not as a third field on the sign up form. The reason is the failure case: a collision on a combined form comes back as an error after the account may already have been created, and the person is left looking at a form that half worked. The claim screen carries the same garden scene backdrop and the same `.gg-card` treatment as the sign in gate.
- **No profile row exists until a username is claimed.** An earlier version auto generated one from the email, which meant a garden full of names like `gardener_4f2a`, and nobody ever changes those. `openClaim` is what creates the row.
- **The uniqueness that matters is on `lower(username)`.** Keni and keni are the same person as far as finding somebody goes, and allowing both is how people get impersonated. The in page check is a courtesy that answers before the button is pressed; the unique index is what enforces it, and the claim button handles losing that race.
- **The username SEEDS the personal garden's name and then they are separate.** `seedNameFromUsername` fills the garden title only when it is empty, so somebody who has already named their garden does not have it renamed under them. If the username is still being claimed when the garden loads, it is taken through `onChange` when it arrives rather than given up on.
- **In the shared garden, a signed in person plants under their username and cannot edit it**, so a flower in the meadow is traceable to a real account. Signed out, the free text box works exactly as it always has, which is what keeps the page something anyone can try without an account. `window.applyAccountUsername` does it, driven by `GardenAccount.onChange`.
- **`friendships` rows are readable only by the two people in them.** The select in `loadFriends` carries no filter of its own on purpose: row level security already restricts it, and writing the rule twice invites the two copies to disagree when only the database's copy is enforced.
- **Only the person who was ASKED can accept**, which is the whole difference between a request and an announcement. That is an RLS policy on update, not a check in the page.
- **A unique index on the PAIR**, `least(requester_id, addressee_id), greatest(...)`, stops two people who request each other at the same moment becoming friends twice and appearing in every list double.
- **Declining DELETES the row rather than marking it**, so the pair are free to ask again another day. A kept row would be blocked by that pair index for good.
- **A friend's row shows the username under the name ONLY when it is a different string.** The test used to be that both fields exist, which is true the moment somebody renames themselves: the rename copies the new name into `display_name` as well whenever that was never set to anything of its own, so the two matched and the row printed the same word twice.
- **The claim screen has a SECOND way in, and its flag cannot get stuck.** It is meant to appear by itself the moment a new account first has a session, from either branch of `boot`, and that is still the only place a profile row is ever created. But an account with no username can do nothing: it cannot be searched for, and a comment it leaves has no name under it. So `openPanel` opens the claim instead of an empty friends panel when there is no profile, and `openClaim` clears `claimOpen` whenever the element is not actually in the page, since a flag cleared only on SUCCESS would otherwise lock the screen out for the rest of the visit.
- **A username can be changed from the friends panel**, through the same uniqueness check as claiming it. The display name follows it ONLY when it was never set to anything of its own, so somebody who has deliberately called themselves something else keeps it.
- **Nobody can rename anybody else, including from a tool.** The update policy on `profiles` is `auth.uid() = id`, so a rename can only be done by that person signed in, or by an owner in the Supabase dashboard's table editor.
- **Every panel closes on a tap anywhere outside it.** `pointerdown` rather than `click`, so it closes as the finger lands rather than when it lifts, and the toggle button is excluded or opening would immediately close again. The shared garden's comment panel makes ONE exception, the garden canvas: that is its own toggle and the sketch already decides there, so closing here too would shut the panel a fraction before the sketch opened it for the bloom just tapped.
- **The button has TWO states and that is the point.** Signed out it says Sign in and opens the sign in card; signed in it shows the username and opens the friends panel. A button that appeared only once you were signed in gave the landing page no way of GETTING signed in, which was exactly the gap there.
- **`data-chip` on the script tag names the corner**, the way `garden-music.js` names its mood. The gardens keep their bottom right; the landing page passes `top`, which puts the chip 8px to the left of the music button, since everything else that page carries is in the top corners.
- **There is ONE sign in form, `mountSignIn`, mounted wherever it is needed**: inside the shared garden's comment panel, and inside an overlay for the chip. The personal garden's gate is deliberately NOT this. It is a full page flow with password recovery and a carry-over offer, and folding it in would make one form answer to two very different situations.
- **Signing in from the standalone overlay RELOADS the page.** A page that signed in halfway through is worse than one that reloads: the personal garden in particular has already decided what to show long before that button is pressed.
- **SENDING IS A DIALOG IN THE MIDDLE OF THE SCREEN, not a panel at the foot.** It sat under the row of share buttons, which on a phone put it below the fold: you pressed "Send to a friend", nothing appeared to happen, and the thing that had happened was off the bottom of the screen. Choosing who a bouquet goes to is the most consequential press on the page and it was the easiest one to miss. It is `position: fixed` and centred, with its own veil as a `::before` so nothing separate has to be built or taken away again, and it closes on Escape.
- **THE CONFIRMATION REPLACES THE FORM.** A sent bouquet is finished, and a small line under a still filled in form invites sending the same thing again. The panel shows who it went to and offers one button, which is out; reopening it brings the form back, so a second bouquet never opens on the receipt.
- **ANY COLUMN THIS PROJECT DOES NOT WRITE MUST NOT BE REQUIRED.** A `bouquets` table left over from an earlier shape can carry one, and a `not null` on it refuses every send with a message naming a column that appears nowhere in the code: `null value in column "share_code" of relation "bouquets"`. Step 7 now CREATES the table rather than only altering it, which it never did, and clears that constraint by name if it is there. **A send that fails on a column you cannot find in the source is this, not the code.**
- **A sent bouquet carries `encodeState(state)`**, the exact string that already travels in a share link, so a sent bouquet and a linked one are the same object and open through the same code. Nothing new renders a bouquet. The send panel stays hidden unless there is an account AND it has at least one friend, since a picker with nothing in it is a dead end rather than an invitation.
- **The pip counts friend requests AND unopened bouquets**, because both are somebody waiting on you.
- **`onChange` fires immediately with whatever is known**, so a caller never has to handle "before the first event" as a separate case.
- **The friends button sits bottom right, and moves up to 60px when `#gg-account` exists.** That chip is built by another module whose session check may still be in flight, so the position is checked again a moment after load.

## The ambient life

**`garden-life.js` at the repo root is loaded by the HERO and both gardens, and there is deliberately only one copy.** Same reason as `garden-music.js`: this project already pays for the same flower maths living in seven places, and a second population of butterflies would drift within a session. The bouquet page does not load it, because a cut bouquet is not a meadow.

**It is written against a raw `CanvasRenderingContext2D` and nothing else**, no p5 and no DOM, which is what lets one file serve two kinds of page. `index.html` passes its own `getContext('2d')`; both gardens pass **`drawingContext`**, which is p5's own 2D context and is already scaled by the pixel density, so drawing on it in p5 units lands exactly where an `ellipse()` would. It does NOT carry p5's `colorMode` or `angleMode`, so everything in the file is CSS colour strings and radians, and every entry point brackets itself in `save`/`restore` so a sketch cannot inherit a stray transform or alpha.

Two entry points, because the life belongs at two different depths:

| call | what | where it goes |
|---|---|---|
| `GardenLife.sky(ctx, w, h, opts)` | the birds | straight after the clouds, so the hills cut them off at the horizon |
| `GardenLife.meadow(ctx, w, h, opts)` | butterflies and motes | last, over the flowers and the labels |
| `GardenLife.drift(ctx, w, h, opts)` | motes alone, across a whole PAGE | one fixed canvas over everything |

In both gardens `meadow` is called **before `drawNewestSparkles()`**, so the burst that fires when a flower is planted is still the brightest thing on screen.

- **The brief was "more lively, not overly crowded", and that is a POPULATION decision.** Two or three butterflies by width, one loose skein of three birds, and about a dozen motes. Everything is slow. A garden with twenty butterflies in it is an aquarium.
- **Everything is placed in BANDS, `[top, bottom]` in the caller's own units.** The defaults come off `opts.horizon`, which is all a garden has to pass, but a page may name any band outright and **the hero does**: its flowers grow UPWARD out of a ground line at the bottom of the picture, where a garden's sit around and below its horizon, so a band derived from one lands in the wrong place on the other.
- **Every vertical figure is a fraction of its band, never a pixel count.** The birds' spread across the skein and the arc of their crossing were both fixed pixel amounts at first, and the hero, which has a short sky, flew its lead bird out through the top of the canvas.
- **A butterfly cannot leave its band, and it is the ARITHMETIC that stops it rather than a clamp.** Home sits at 0.35 to 0.65 of the band and the two sines together can move it at most 0.312 of the band, so the deepest it reaches is 0.962. A clamp was the alternative and it reads as a ceiling the butterfly is sliding along. Sideways it may leave the scene entirely, which is different and wanted: one that never goes anywhere is on a leash.
- **Two sines of unrelated periods on each axis, never one.** One sine is an oval track and reads as a machine. Two that do not divide into each other never quite repeat.
- **The heading comes from where the butterfly is ABOUT to be**, sampled 0.18s ahead, not from a stored angle, so a turn reads as a turn rather than as a slide.
- **The wings never shut completely.** `open` bottoms out at 0.26, because a butterfly edge on for a whole frame simply disappears.
- **The sky is EMPTY most of the time and that is the design.** One skein crosses for 30 seconds and then the sky is clear for 22, with the direction flipping each pass and a new lane inside the band. A sky with birds permanently in it stops being a sky with birds in it.
- **The population is deterministic**, seeded through one `rnd(seed)` rather than `Math.random`, or the meadow would differ on every reload and, worse, on every rebuild after a resize.
- **It is rebuilt only on a real size change**, more than 40px either way. Rebuilding on every pixel of a window drag would restart every flight path in mid air.
- **Reduced motion gets the scene POPULATED but FROZEN**, at a fixed `t` of 8.4 seconds, rather than emptied. The butterflies are part of the picture; it is only their movement that was opted out of, and the hero's sway makes the same choice by keeping its flowers and setting its amplitude to zero. That moment was checked rather than picked: all three butterflies come out between 0.78 and 1.00 open, and the birds are a quarter of the way across.
- **Sizes come off a 1440 wide logical scene**, which is the gardens' `BASE_W` and the hero's logical width, so both land on the same figure with no page specific tuning. Clamped to 0.62 and 1.25, or a phone draws butterflies too small to read as butterflies.
- **`drift` is the landing page's, and it runs on its own fixed canvas**, `#page-dust` at `z-index: 6`. Six is measured, not guessed: every section's own content tops out at 5, and the flower modal is 300, the music button 260 and the side nav 9000, so the motes sit over the whole page and under all three.
- **The motes belong to the SECTIONS, not to the window.** They are held in page coordinates and drawn at `pageY - scrollY`, so scrolling carries them past exactly like the copy does. The first version held them in viewport coordinates, and the same dozen motes then hung in the same places however far the page was scrolled, which reads as dirt on the screen rather than as air in a room. Each band gets its own count from its own height, and only what is on screen is drawn, so a long page costs no more per frame than a short one.
- **`drift` carries BUTTERFLIES too, about one per section**, held in page coordinates like the sparkles and kept inside their own band by the same headroom rule the gardens use. They are drawn after the sparkles, so the one solid object on the canvas is never behind the specks of light. Measured across the landing page: 9 of 15 viewport positions down a 7511px page have one in view, which is present without being crowded.
- **The population is rebuilt only when the page's shape changes**, keyed on a signature of the width and every band's top, bottom and tone. Rebuilding on scroll would re-seed every mote thirty times a second.
- **A mote is a SPARKLE, the four pointed star the gardens throw around a newly planted flower, not a soft dot.** Two stacked circles was the first version and it read as jitter rather than as light: a dot two pixels across, moving a third of a pixel a frame and pulsing its radius, is just antialiasing changing its mind. A star has a shape to recognise, so the eye reads it as one thing turning. The geometry is `drawNewestSparkles` exactly, four outer points with the inner corners at 0.35 of the radius, over a soft halo. What differs is the SPEED: the garden's sparkle runs off `frameCount` at a rate that suits a burst lasting a few seconds, and these hang around as long as the page is open, so they are slowed right down and driven by the clock, which also makes them frame rate independent.
- **The brightness twinkles and the size barely moves.** A radius that swings hard is the other half of what read as jitter, along with sub pixel drift, which is why the drift and rise speeds went up rather than down.
- **A mote has TWO palettes and it is not decoration.** On a dark ground it is white and reads as light. On CREAM, which is most of the landing page, white is invisible and it has to go the other way, sitting DARKER than the ground: the pale tones become a warm gold and a soft teal, at 1.35 times the alpha to make up for the smaller contrast. `opts.toneAt(y)` answers the only question the module cannot answer for itself, is the ground behind this point dark, and the landing page answers it by measuring `#wisdom` and the footer once in PAGE space and adding `scrollY` per frame. Reading pixels back off the page every frame was the alternative.
- **The hero's birds are on their OWN canvas, `#hero-sky`, and not on the meadow canvas.** The meadow canvas begins where the meadow does, well below the copy, so a bird drawn in it could only ever fly just above the flowers, which is not where a bird is. `#hero-sky` covers the whole hero section at `z-index: 3`, over the clouds and the sun at 2 and under the copy at 5, and its band is 8 to 30 percent of the hero's height. Measured after: birds at y 105 to 140 with the clouds at 92 to 146, so they fly among them.
- **The hero sets its own bird rhythm**, `cross: 26, gap: 8` against the gardens' 30 and 22, plus a heavier ink and a slightly larger scale. A visitor reads the top of a page for a few seconds and then scrolls, so a flock that is away for twenty two of every fifty two seconds is one most people never see at all.
- **Painted only while the hero is on screen**, since there is nothing to look at once it has scrolled away.
- **The dust canvas re-sizes itself from `paint()` rather than trusting `measure()`.** A canvas sized while the window reports zero, which happens in a hidden tab and in some embedded views, stays zero for good otherwise: no resize event ever fires to correct it, and the page then carries an empty canvas with nothing on it and no error anywhere.
- **Verifying any of this needs `redraw()` first.** p5's `draw()` is rAF driven and the browser pane here is often hidden, so a garden sits at `frameCount` 0 with an empty canvas and a pixel sample reports nothing. This cost a full round of chasing a bug that did not exist, twice over: the second time the page was simply running a CACHED copy of the sketch, which `draw.toString().indexOf("GardenLife")` settles in one line.

## FOUR BUGS IN A ROW WHOSE CAUSE WAS `!important`, or the lack of it

The gardens build their interface with p5.dom and inline `.style()` calls, so a plain stylesheet rule cannot reach any of it. Every one of these looked like a different bug and was the same one:

- **The Garden Tips would not open.** The sketch sets `pointer-events: none` on `#tips-card` inline, and the phone block's `pointer-events: auto` lost to it, so the heading never received the tap. Nothing about the fold was wrong; the card was not listening. **Verified with `document.elementFromPoint` at the heading's centre**, which is the only test that answers "what would a finger land on here"; a dispatched click bypasses hit testing and passes over a card nobody can press.
- **The camera sat out of the row.** `#save-btn` has its `top` and `right` set inline by the sketch, so it kept its desktop 20 and 154 while the other three moved to the phone's 16 and their own slots. Four pixels low and sixteen to the left of a row it belongs to. The slots are 12, 54, 96, 138.
- **The garden's name came out in two sizes.** `#gg-name` is an input, so the phone block's blanket 16px floor on text fields raised it and left the "'s Gratitude Garden" beside it alone. **It cannot be corrected with another `!important` either**, because any `!important` beats the inline size `fitTitle` computes; it has to be LEFT OUT of the floor, which is what the id is for. `NAME_PX_MIN` is 16 on a phone instead, so `fitTitle` is the one thing that sizes the title and iOS still never zooms on it.
- **The friends panel peeked up from the foot of the landing page.** `translateY(102%)` clears a closed panel by two percent of its own height, which on a phone is about twelve pixels, and an address bar sliding in and out moves the sums by far more. It carries `visibility: hidden` when shut now, which no arithmetic can get wrong, and the phone rule uses `calc(100% + 40px)` so the clearance does not shrink with the panel.

**The rule this leaves behind: before changing a garden's layout in CSS, check whether the sketch sets that property inline.** If it does, the rule needs `!important` or it does nothing. And if the value is COMPUTED inline, as the title's is, `!important` is the wrong tool and the rule has to exclude it instead.

**Home is a HOUSE, not a back chevron.** A chevron pointing left means "the previous page", which is what the browser's own button underneath already says. This link always goes to one particular place, and the glyph everybody reads as that place is a house. On a phone it is the glyph alone, with the word in `aria-label`.

## Stems, halos, taps and the corner icons (a round of phone fixes)

- **A FLOWER PLANTED ON A PHONE WAS SAVED SHORT FOR GOOD.** `addFlower` in the personal garden multiplied the stem by 0.7 under 720px and then stored `stemLen / BASE_H`, while the layout reads it back as `stemNorm * height`. So a phone-planted flower carried about two thirds of its stem into storage and the phone layout shrank it again. The stem is now stored as `stemLen / height` with no narrow-screen shrink, and the narrow cap in `updateResponsiveFlowerLayout` is the one place a phone shortens stems. **`STEM_FLOOR` lifts flowers already saved short** to their layer's lowest planting range on every layout; nothing in a saved flower says where it was planted, so the floor is the only honest repair. The shared garden never had this: it recomputes stems from `baseBands` on every layout.
- **`BLOOM_BOX` WAS WRONG AND IS RE-MEASURED.** Painted through `drawBloom` at R 60 and read back, identically in both gardens, the old table ran about 8 percent large and 0.05 R low, the lotus sat 0.08 R low of its petals, and the lavender was recorded at 0.48 R wide for a spike that paints 0.26, which is why it wore a wide fog. The halo is now 0.14 dark with an edge a quarter of the radius.
- **`bloomShadow` is a RADIAL GRADIENT in both gardens, not the canvas shadow API.** The old version drew an ellipse 6000 units away and dragged it back as a shadow, which is correct by the spec and came out wrong on an iPhone, where WebKit treats shadow offset and blur differently under a scaled context. A gradient is drawn in the current transform like any shape, so it needs no pixel density arithmetic. Same 0.18 darkness and 0.9 fit; the soft edge is `R * 0.32` with no 6px floor, since the floor made the edge nearly as wide as a small phone bloom.
- **THERE IS NO HOVER BOX IN EITHER GARDEN.** A flower is read only from the card a click or a tap opens, one look on every device. Hovering sets `data-gg-hot` on the canvas, which `garden-cursor.js` lists as clickable, so the cursor says a flower can be pressed. `drawHoverTooltip` still exists in both sketches and is no longer called.
- **The two cards are the SAME card**: 224px, the same ground, corner and shadow, the species as a small serif heading with a dot of the flower's own colour, and full width dark actions. Only what it says differs.
- **`keepFlowersOnScreen()` holds each flower's drawn x in far enough for its whole date or name label and bloom**, in both gardens, at the end of the layout. Stored `xNorm` is untouched, so a wide layout does not move; a flower planted at a wide window's edge no longer hangs off a phone.
- **A TAP ON A FLOWER SHOWS A SMALL CARD in both gardens, never the whole thing.** Personal: `showFlowerCard` in the sketch, species, meaning, the date written out and a Read this day button that opens the book. Shared: `GardenSocial.peek` in `shared-garden-social.js`, the sentence, who planted it, a heart that likes in place (sign in if signed out) and a comment count whose button opens the full panel. The shared card reads counts only; the post row is still created lazily on the first like or comment. Both hover tooltips return early while their card is open, or the same words show twice.
- **The shared garden has no name step as a screen.** `goToFlowers()` skips it. Signed in, the account's username is used; signed out, the same field is moved to the top of the flower screen (`#select-name`). The old step is still built because its note and planted-today check are reused.
- **The shared flower picker is two columns of wide 68px tiles**, all eight on one phone screen, overridden at the END of `shared-garden-style.css` with `!important` and scoped to `#select-wrap`. Its previews are a 76 square buffer at density 2 shown at 56.
- **Home matches the icon row, from `garden-cursor.js`.** Its house is redrawn on the 24 unit grid at stroke 2 by `swapHomeIcon()`; on a phone it is a 34px circle at 16 and 12, on a laptop the pill stands 38 tall with an 18px icon, which is the other icons' 1.5px line. The selector is `html body a#back-to-home` so it outranks each page's own `!important` phone rules and the inline style.
- **GARDEN TIPS ON AN IPHONE.** It worked in every emulation and not on the phone. The heading sat about 20px above Safari's floating toolbar, which takes taps that close for itself, and it was a plain heading. It is lifted to `bottom: calc(64px + safe area)` and given `role="button"`, `tabindex`, and a `touchend` toggle that ignores the click the phone fires after it. **Anything tappable near the bottom of a phone screen needs the same clearance.**

- **Garden Tips OPENS AS A CARD on a phone**, a cream panel with a shadow, since opened on the grass its list ran across the flowers unreadably.
- **Titles no longer disappear under the corner icons on a phone.** Once a page has scrolled, `garden-cursor.js` sets `data-gg-scrolled` and a frosted strip sits behind the icons, so copy passes under a band. The gardens' step screens scroll inside fixed `.gg-wrap`s, which now start at 58px, below the icon row. **Home's colour is pinned** to the icons' dark teal, because the personal garden's phone stylesheet sets every link to `color: inherit !important`.

On a drag canvas the tooltip is hover only.

## Three phone faults with one shape: something invisible eating the tap

**A BUTTON THAT NEEDS PRESSING TWICE IS ALMOST ALWAYS `:hover`.** Safari on iOS has no pointer to hover with, so it fakes one: the first tap on anything carrying a `:hover` rule APPLIES that rule instead of activating the thing, and the tap that does the work is the second. Every lift and colour change in this project was a bare `:hover`, so every one of them could eat a tap. All four stylesheets now turn those effects off under `@media (hover: none)`, which costs nothing, since a lift means nothing on a screen with no cursor to lift away from.

**The other half is the ZOOM DELAY.** A browser waits about 300ms after a tap on anything it might have to double tap to zoom, and a press that does nothing for a third of a second reads as a press that did not register. `touch-action: manipulation` on `button, a, [role=button], summary, input[type=range], label[for]` in all four stylesheets says these are never zoom targets and removes the wait.

**`hidden` LOSES TO ANY AUTHOR RULE, and that is what made the bouquet's foot bar unhideable.** `[hidden]` works through the browser's own stylesheet, which every author rule outranks, so `.bq-sticky-bar { display: flex }` in the phone block kept the bar on screen however many times the code set `bar.hidden = true`. Reading `bar.hidden` back said `true` while the thing was plainly visible, which is the worst kind of disagreement to debug: the JS and the screen each looked right on their own. It needs `.bq-sticky-bar[hidden] { display: none !important }`, in the same block, because that is the rule it is fighting. **Anything in this project that toggles `hidden` on an element whose display is set by a rule needs the same line.**

**THE SCROLL JITTER WAS THE PAGE DUST.** Six sticky canvases re-rasterising thirty times a second on top of a scroll asks the phone to repaint the layer underneath while it is already compositing the scroll. They now skip painting entirely while `html[data-gg-scrolling="1"]`, which is the flag `garden-cursor.js` already sets, so there is one answer to "is the page moving" rather than two. The motes drift a few pixels a second, so half a second of stillness under a thumb is invisible.

**A CARD THAT SEEMS TO OPEN UPWARD is the column moving, not the card.** Opening one closes the others, and if a card higher up was the open one, several hundred pixels vanish ABOVE your thumb and the whole page slides. Nothing animates upward. Scrolling the opened card's own top back to the top of the screen is what makes it read as opening downward from where you pressed.

## Type

**The font is Fraunces, and it is IN the repo.** `Fraunces.ttf` and `Fraunces-Italic.ttf` sit at the root with `Fraunces-OFL.txt` beside them. It replaced Mauritius, whose two files were named by `@font-face` for the project's whole life and never actually existed, so every page had always been rendering Georgia. **If a heading ever looks wrong, check the font is loading before changing a number.**

It is **one variable family** with a weight axis of 100 to 900. The italic is a second face on the same family, so `font-style: italic` picks it up on its own and the bouquet's letter needs nothing else.

**All four pages share it. What differs is the WEIGHT.** The landing page's headings are 700; the two gardens and the bouquet are **600, a real semibold**. That weight was wanted from the start and was impossible under Georgia, which renders 600 identically to 700; measured on Fraunces the same string runs 472.49, 489.11 and 505.73px at 400, 600 and 700, so 600 genuinely sits between. **Buttons are 700 everywhere and are a separate rule.**

**`font-variation-settings: 'SOFT' 50, 'WONK' 0` is on the heading rules, not globally.** SOFT rounds the terminals, which is the friendliness the font was picked for. WONK stays 0 because its slanted alternates are charming in a wordmark and distracting in a paragraph. Body text is Arial and is untouched. The personal sketch sets the same axes inline on its name field and suffix, since inline wins there.

Inline wins over the stylesheet, so the personal sketch's four card headings, its name field and its suffix all set `font-weight: normal` in the JS, and `fitTitle`'s measuring span has to carry the same weight or the width it computes is wrong.

**Georgia has exactly TWO weights, which is why the ratios below exist.** While Georgia was the fallback, 300/400/500 all rendered at 602.72px and 600/700/800 all at 701.91px, so a semibold was impossible and the titles had to earn presence from their RATIO to the line under them. Fraunces fixed the weight problem, but the ratios were right on their own merits and stayed.

| | title | sub | ratio |
|---|---|---|---|
| landing hero | up to 68 | 17.85 | about 3.4 |
| gardens `.gg-title` / `.gg-sub` | 42 | 16 | 2.63 |
| bouquet `.bq-title` / `.bq-sub` | 28 | 13 | 2.15 |
| the garden's own name and its note | 28 | 13 | 2.15 |

They were 1.73 and 2.22 and read flat next to a 3.4 hero. `fitTitle` derives the note from the title at 0.46, so that ratio holds at every shrunk size. **Check for an inline size before changing `.gg-sub`:** the personal garden's prompt cards set theirs in the JS, so the stylesheet value governs the shared garden's landing and little else there. **Primary buttons are weight 700 everywhere.** The gardens' `.gg-btn` was weight 400 and the personal garden's inline buttons were 600, which made a garden's main action the softest button in the project next to the landing page's bold ones. The two garden pages used `"Inter", sans-serif` throughout and the bouquet used plain `Georgia`, so the four pages read as four websites.

**The bouquet page sets `html { font-size: 17px }`,** the same root the landing page sets, because every size on that page is in rem and on the browser default of 16px they all came out about 6 percent smaller than the same text next door.

**A bouquet step heading is 26px and its line under it 15px.** The sub is not `.gg-sub`'s 18px: that size belongs under a 40px title, and under a 26px one it was nearly as large as the title itself. The personal garden runs a 13px line under a 23px heading, a ratio of 0.57, and 15px under 26px is 0.58.

**Why 26 and not 40.** The gardens carry four heading sizes and it matters which one a thing matches. `.gg-title` at 40px is a title standing on its own above everything, used for Daily Reflection and Choose Your Flower. A heading *inside* a garden card is 26px, the personal garden's Your Flower `h2`, or 23px for its prompt `h3`s, and the shared garden's confirm title is 28px. `.bq-title` sits at the top of a card on all seven steps, so it is the 26px one; at 40px it was the gardens' loudest size used in their quietest position. `.bq-sub` is 18px, which is `.gg-sub` exactly. **Do not widen the flower step to give a heading room:** at 900px its `auto-fit` grid holds four columns and the eight species fall 4 and 4, and past about 960px it becomes five and they fall 5 and 3.

The `@font-face` rules are repeated in all four stylesheets, with `../` paths in the three sub-pages, so every page loads the same family from the same two files at the repo root.

**The personal garden's own title is 26px serif, and it has to fit.** It was 15px Arial against a 21px serif "Garden Tips" in the corner, so the loudest heading on the page was a side note. 26px is the size a heading inside a card takes across this project, and the serif every other page puts its headings in; the note under it is 15px, the 0.58 ratio the bouquet's steps use. `#name-wrap` is `nowrap` and centred so it cannot fall back to a second line, and the field takes 30 characters, so **`fitTitle()` measures the rendered width and shrinks the whole title until it fits**, down to a 13px floor, rather than picking a size from a breakpoint. It runs on load, on every keystroke in the name and on resize, and it returns early under a 200px viewport, since a hidden tab reports 0 and would otherwise shrink the title to the floor and leave it there. The name field carries no right padding: with 4px there the box held the name away from the `'s` and the title read as "Keni 's Gratitude Garden".

Headings on the garden pages come from two places. `.gg-title` and `#tips-card h3` are in the stylesheets; the smaller card headings are built by `buildUI()` with p5.dom and carry inline `font-size` and `font-weight`, so those change in the JS. Inline wins over the stylesheet, so setting a heading's font in CSS alone will not take.

## `garden3d/`, a SEPARATE exploration, not part of the site

**Nothing in `garden3d/` is loaded by the four pages, and nothing in the four pages loads it.** It is a spike for a possible thesis direction: the same garden as a cosy low poly, avatar based, isometric 3D space, after Animal Crossing and Cozy Island. **The web version stays exactly as it is.** If that ever stops being true, this note is wrong.

- **It answers ONE question**: at the distance the game would be played at, does each species read as itself? Everything in it exists to test that and nothing else. There is no avatar system, no persistence, no interaction beyond the controls.
- **Three.js r169 is VENDORED** at `garden3d/lib/three.module.min.js`, 687KB, imported as a plain ES module. No build step, no CDN at runtime, which is the same rule the rest of the project follows.
- **No model files, ever.** `flower-kit.js` holds five primitives (petal, stem, spike, disc, and the merge helper) and a parameter row per species. That is what keeps the person's chosen HUE working, exactly as in 2D, and it reuses the hues and petal counts `SPECIES` already carries in `bouquet-sketch.js`.
- **PITCH is the one parameter the 2D version does not have**: how far a petal leans from vertical. Tulip 8 degrees stays a closed cup, daisy 78 is flat, lily 100 is swept back. Pitch does most of the work of telling them apart.
- **THE SILHOUETTE TEST EARNED ITS PLACE IMMEDIATELY.** With colour removed, the daisy and the sunflower were the same shape: a ring of petals with a centre, differing only in size. The same failure the chrysanthemum had in 2D. The fix was not petal count, it was HABIT: the daisy is a clump of three low heads, and the sunflower is one tall stem with a big disc that NODS forward 24 degrees. Nodding is also the hook for the behaviour idea, a head that follows the sun.
- **The growth timings are the web version's, unchanged**: `GROW_RISE` 3400ms, `GROW_OPEN` 1700ms, a cubic ease out on the rise and a smoothstep on the opening, the bloom scaling from 0.18. A flower grows at the same speed in both versions, which is continuity rather than coincidence.
- **All interface is HTML over the canvas**, and that is the architecture the real thing would use: never build a text field in WebGL, since the reflection writing has to stay accessible and keep the project's own type.
- Measured: 60fps at 1400 by 900 with all eight species, fourteen plants and a pond, 704KB on disk including three.js.

**ALL EIGHT ARE IN NOW, and the last three are the ones that taught the most.**

- **RINGS are the second assembly, and the rose and the lotus are one routine with different numbers.** `addRings` builds a bloom as concentric rings of petals whose pitch climbs from nearly closed at the middle to past flat at the outside, each ring turned half a step off the one inside it so petals fall into gaps rather than stacking into columns. That the two hardest blooms came out of one routine is the kit doing its job.
- **A ROSE PETAL IS ALMOST AS WIDE AS IT IS LONG, and getting that wrong is what made the first three attempts a hollyhock.** Narrow petals at climbing pitches spiral upward into a cone of frills. Wide ones overlap sideways and close into a ball. Each ring also sits a little LOWER than the one inside it; stacked at one height the climbing pitches read as a staircase.
- **The rose's outer ring is pushed PAST flat, to 94 degrees**, so the ball sits on a flange of splayed petals. In silhouette a plain ball of petals is a tulip bud drawn rounder, and the flange is what tells the two apart. It is also a spray of two heads, the same habit fix the daisy took.
- **THE SAKURA IS A TREE, and that is the finding, not a style choice.** As one blossom on a stem it is a five petalled pink flower, which is a daisy in another colour: the same collapse the chrysanthemum had in 2D and the sunflower had here. As a small tree it is the only thing in the garden with a canopy, it gives the plot vertical variety, and it is something an avatar can stand under, which is what "reflection and presence" should be.
- **A canopy is many small blobs, all at the SAME detail.** One sphere is a lollipop. Sixteen icosahedra at radius 0.1 to 0.17 give a bumpy edge that reads as blossom. Mixing a detail 0 with a detail 1 put three hard crystals in a canopy of soft ones, which reads as a fault rather than as variety; the depth comes from two tones instead.
- **THE LOTUS NEEDED WATER, so the plot gained a second kind of place.** Its meaning is rising out of something, so the pads it rises from are half the picture. That also makes it the one species that cannot be planted just anywhere, which is a rule the 2D version had no way to express: in 3D a plot with soil, water and open grass is a design surface the web version does not have.
- **The notch is what makes a green disc a lily pad.** A `CylinderGeometry` with a `thetaLength` of 1.83 PI leaves the wedge out. Four pads at three sizes, turned at random, and the bloom on a stem tall enough to clear their outline.
- **Every petal material is registered with its own lightness offset** (`userData.tint`), so one hue slider moves a rose's five rings together and keeps the depth between them. A single `petalMat` could not have held a bloom built from rings.
- **The silhouette test passes at garden and wide distance with all eight**, and the two new plant types are the easiest of the lot to name: a tree is a tree, and pads are pads.

**THE LOOP IS IN: reflect, choose a spot, watch it grow.** The species test asks whether you can tell them apart; this asks the question that comes after it, whether PLANTING one feels calm. Three things make it a loop rather than a placement tool, and each earned its place.

- **The same three questions and the same weighted vote.** Rating 4, what shaped the day 3, two per keyword hit in the sentence, `chooseSpecies` in `spike.js`. **The sentence is not optional decoration: without it the rating always wins and the second question is a button that changes nothing**, since 4 beats 3 on its own. Verified in the page: Okay plus People alone gives a sakura, and adding "love my family" turns it into a rose.
- **WHERE a thing may grow is the rule that makes the plot a place.** `PLOT` gives each species its ground (the bed, the water, open grass), its spacing and how far back the avatar stands. A lotus refused on the soil and a sakura refused on the bed both say WHY in words, at the top of the screen: a marker that simply will not turn green is a puzzle, not an answer.
- **The spacing rule takes the AVERAGE of the two gaps, never the larger.** A tree asks 1.3 of another tree, a daisy 0.3 of another daisy. Taking the larger made a tree demand its own 1.3 from every daisy in the bed beside it, which left the open grass unplantable for the one species that has to go there.
- **THE BED MUST NOT BE FULL.** The two specimen rows filled it exactly, so "pick a spot" became a hunt for the one legal pixel. The bed is deeper now and the rows sit back, leaving a free strip along the front. **A garden with no room in it cannot be planted in, which is obvious in hindsight and was not obvious while the bed was a test rig.**
- **The avatar WALKS there, and stops on the FAR side of the spot from the camera.** Stopping short along the walking line put it between the camera and the flower it had just planted, hiding the one thing the person was waiting to see. It takes the camera's current angle, so this holds at all four turns, and it is pushed out of the pond if the far side of a lotus is water.
- **The flower is created at the CLICK with its birth set in the FUTURE**, `now + travel`, so it waits in the ground until somebody is there to plant it. `growth()` already drew a flower whose moment had not come, so nothing needed to change for that.
- **A loop with no end just stops.** The closing line is timed to the frame the bloom finishes opening, at `born + GROW_RISE`, and says the species and its meaning.
- Measured: 60fps at 1400 by 900 with the plot, the pond, the tree and sixteen plants.
- **What the loop has NOT answered yet**: a tree grows to full height in the same 3.4 seconds as a daisy, which is the web version's timing used where it does not belong.

**THE AVATAR, AND CUSTOMISATION TIED TO REFLECTION (`avatar-kit.js`).** The capsule stand in is gone. The avatar is built the same way the flowers are, from primitives and a parameter row, so **a look is DATA**: a row of numbers survives being saved against an account, sent to a shared garden and read back next year, where a mesh does not.

- **THE WARDROBE IS FILLED BY PLANTING, NOT BY A SHOP.** Every keepsake belongs to one species: plant a daisy and you keep a daisy chain, plant a sunflower and you keep the sun hat. Nothing is bought, nothing is timed and nothing can be missed, which is the difference between a reward and a record. At the end of a month the avatar is wearing an account of what the person noticed. A locked tile says which flower unlocks it, so the wardrobe doubles as a reason to come back without ever nagging.
- **A keepsake is worn straight away ONLY if that slot is empty**, never over something already chosen. A gift that silently takes off what you were wearing is not a gift. Tapping a worn keepsake takes it off, so a slot is never a trap.
- **The keepsakes ARE the flowers.** `buildBloom` was extracted out of `buildFlower` so a daisy in the bed and a daisy on somebody's head are one piece of code. That is the kit paying for itself a second time: the 2D version pays for the same flower maths in seven places, and the obvious way to build a flower crown would have made an eighth.
- **What is worn is the FLOWER, never the HABIT.** The sakura is a tree in the ground, and a blossom clip is two blossoms: `buildBloom` gives the sakura a five petalled wearable row of its own rather than putting a small tree on somebody's head. The lotus is carried on its own pad, which is the same rule read the other way.
- **Three slots, head, shoulders and held, so three can be worn at once** and no two keepsakes ever fight for the same place. Eight keepsakes across three slots is a wardrobe; eight in one slot is a list.
- **A BRIM IS MEASURED AGAINST THE HEAD.** The sun hat was drawn at 0.44 against a head of 0.23, which is what a sun hat is, and from the only angle this game has, above, it read as a mushroom and swallowed the shoulders. It is 0.33.
- **The arms exist for the keepsakes, not for the figure**, since three of the eight are carried and a held flower with no hand under it floats beside the body like a bug. They are a SLEEVE and a HAND, not one bare capsule: in the skin tone they read as two pale blocks stuck to a jumper.
- **The eyes are not decoration.** With a blank head there is no telling which way the avatar is facing, so turning to face the camera in the wardrobe, and turning toward a flower after planting, both said nothing at all. They also have to sit BELOW the hairline, or the hair cap swallows them.
- **The wardrobe brings the camera to the avatar AND DROPS ITS PITCH.** Choosing a hat while the wearer is thirty pixels tall across the garden is choosing blind, and the garden is read from above where a head is mostly hair. The angle round the scene never changes, only the target, the width and the height, so it is the same world seen closer rather than a second camera with its own rules.
- **"Unlock everything" is a TEST control and says so on the button.** The spike keeps nothing between reloads, so without it the wardrobe can only be seen by planting eight flowers again. It is not part of the design.
- **A measurement trap worth keeping**: the browser pane throttles `requestAnimationFrame` while it is not painting, so an fps sample taken straight after a tool call reported 12. Taken after a screenshot, which forces a paint, the same scene reports 60. Force a frame before measuring, the same way p5 needs `redraw()` before a pixel sample.

**THE SHARED GARDEN IS A SECOND SCENE, `shared.html` and `shared-scene.js`, AND IT HAS NO AVATARS.** The 2D page is one room a day, keyed on the date, that anybody can plant one flower in with a typed name and a sentence. `garden3d/index.html` is your own plot; this is the day everyone is in.

- **No avatars, and that is the design rather than a saving.** A private plot has one person in it who walks around. A shared day has twenty strangers who were each here for a minute, and twenty avatars standing about in a field is a lobby. What is left of somebody is their flower, which is what the 2D page already says.
- **ONE TREE, AND EVERYONE PLANTS AROUND IT.** A field with no middle reads as a grid of strangers; a circle reads as people who turned up to the same place. It is a sakura, the species whose meaning is being present somewhere.
- **THE RINGS ARE THE DAY.** Slots fill outward in the order people arrived, so the first person of the morning stands nearest the tree and the last stands at the edge, and **the camera widens as the day fills** (`fitted()`): an empty morning is a small garden and a full evening is a wide one. The four rings hold 56 people.
- **EVERYBODY GETS THE SAME AMOUNT OF ROOM, so a species that needs more is planted smaller.** A sakura in a ring slot is a whole tree and it swallowed its neighbours and the landmark in the middle; in a slot it is a SAPLING at 0.58. A lotus cannot stand on grass, so it brings its own pool, one slot wide. **One person's choice cannot be allowed to take three slots**, which is a rule a shared garden needs and a private plot does not.
- **The names are HTML tags positioned by projecting each bloom's own world point**, the same rule as every other piece of text here: the project's type, readable by a screen reader, crisp at any distance, and no font texture. **Only the hovered flower's name is shown, plus your own always**, because twenty names at once is a field of labels with a garden somewhere behind it.
- **The card sits BESIDE the flower, on the side away from the middle, and it took two wrong placements to get there.** Anchored above and clamped, it came to rest on the title card in the corner. Flipped below, it covered the very flower it was describing, which is worse. Beside it can do neither, and putting it on the outward side keeps the tree and the early rings visible while one flower's line is read.
- **`growth.js` is a module now, and that is the 2D lesson applied before it cost anything.** The web project carries the growth sequence twice, character for character, with a note saying to edit one and edit the other. There are two scenes here, so the same crack was about to open; `GROW_RISE`, `GROW_OPEN`, the two easings and `growFlower` live in one file that both import. **`growFlower` writes the whole scale**, so a sapling has to be told its size again each frame, which is the cost of that and is worth it.
- **One flower a day, and the button SAYS so rather than disappearing**: a control that vanishes reads as a fault.
- **NOTHING HERE IS NETWORKED.** The day is fourteen seeded entries, invented for the spike, so a shared garden can be looked at while there is nobody to share it with. The real thing keeps the split the 2D page already has: the living room in p5.party, and likes and comments in Supabase. The like button toggles locally only; one like per person stays a database rule, not a page rule.
- Measured: 60fps, and the two pages link to each other.

## Conventions

- Indentation is inconsistent (the shared sketch is largely unindented at top level). Match the surrounding block rather than reformatting; whole-file reformatting would bury real diffs.
- Colors are HSL throughout the sketches. Flowers carry `hue` (user-chosen), plus `sat`/`light` from `defaultSat(species)`/`defaultLight(species)`. Petal shape ratios live in `speciesShapeCfg()`.
- p5 sketches use `angleMode(DEGREES)` and `noiseSeed(9999)`; keep deterministic seeding when adding generative detail.
- The vendored `*-p5.min.js` and `*-p5.party.js` are minified third-party bundles, never edit them.
